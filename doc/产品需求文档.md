# 高校绩效计算系统：MVP 产品需求文档

## 1. 产品概述

### 1.1 产品名称

高校绩效计算系统（暂定名：NumCounts）

### 1.2 产品背景

高校绩效管理规则通常复杂且变化频繁，涉及教学、科研、管理、社会服务、奖励等多个维度。不同学院、岗位、职级、年度或考核周期往往适用不同的计算方式。

传统以手工表格处理绩效的方式存在以下问题：

- 规则分散在多个文件中，维护成本高；
- 公式容易被误改，计算结果难以追溯；
- 规则变更后需要重复修改大量表格；
- 数据录入、校验、计算和发放之间缺少统一链路；
- 教职工难以理解个人绩效结果的来源。

本系统以“单张规则表”为核心，通过统一的输入、函数和输出模型，实现可配置、可计算、可追溯的高校绩效核算。

在此基础上，系统引入插件和工作流两层能力：插件将复杂、重复的计算逻辑封装为业务函数，工作流则面向操作员编排数据导入、计算、校验、汇总和导出等步骤。无论插件或工作流如何扩展，底层规则、输入和结果仍以表结构保存和追溯。

### 1.3 产品定位

一个面向高校绩效管理员的轻量化、可配置绩效计算工具。

系统不预设某一所高校的固定规则，而是提供规则配置与计算内核，使管理人员能通过维护表格适配本校、本学院或本年度的绩效政策。

## 2. 产品目标

### 2.1 核心目标

- 用一张规则表描述绝大多数绩效计算规则；
- 支持管理员无需编程即可调整绩效计算逻辑；
- 自动生成个人绩效总额、分项结果及计算明细；
- 支持规则、输入数据和计算结果全流程追溯；
- 在规则频繁变化的场景下，降低维护和核算成本。

### 2.2 MVP 成功标准

- 管理员可创建或导入一份绩效规则表；
- 管理员可导入教师或员工的绩效原始数据；
- 系统可按规则自动计算绩效结果；
- 每条结果可查看使用了哪些输入、规则和公式；
- 支持导出最终结果及计算明细。

### 2.3 非目标

MVP 阶段暂不覆盖：

- 工资发放或财务系统直连；
- 多级审批流；
- 移动端应用；
- 复杂组织权限体系；
- 自动采集科研、教务或人事系统数据；
- 大规模跨校数据协同。

## 3. 用户与使用场景

### 3.1 目标用户

| 用户角色 | 主要职责 | 核心诉求 |
|---|---|---|
| 绩效管理员 | 配置规则、导入数据、发起计算、导出结果 | 快速调整规则，减少人工核算 |
| 学院管理员 | 维护本学院数据，查看核算结果 | 保证数据准确，处理异常 |
| 教职工 | 查看个人绩效结果与明细 | 理解结果来源，发现问题 |
| 财务或人事人员 | 使用最终绩效结果进行后续处理 | 获得准确、标准化的数据 |

### 3.2 典型使用场景

#### 场景一：年度教学绩效核算

管理员导入教师课时、课程类别和课程系数，配置教学绩效公式：

`教学绩效 = 课时数 × 课程系数 × 课时单价`

系统批量计算每位教师的教学绩效。

#### 场景二：科研成果积分计算

管理员导入论文、项目、专利和获奖数据，根据成果等级、作者排序及学院政策计算科研绩效。

#### 场景三：规则调整后重新测算

学校调整某类课程的系数，管理员仅修改规则表中的函数或条件，重新执行计算，无需重做全部原始表格。

#### 场景四：个人结果核查

教师查看个人结果，系统展示其原始输入、命中的规则、执行公式和最终分项金额。

## 4. 核心产品模型

### 4.1 总体模型

系统由三类核心数据组成：

`输入数据 + 规则函数 + 输出结果`

| 模块 | 含义 | 示例 |
|---|---|---|
| 输入 | 用于计算的原始业务数据 | 课时数、论文等级、项目经费、岗位等级 |
| 函数 | 绩效计算公式、判断条件和限制规则 | `课时数 × 系数 × 单价` |
| 输出 | 系统计算得到的结果 | 教学绩效、科研绩效、总绩效 |

系统通过“表、插件、工作流”三层协同工作：

| 层级 | 面向对象 | 核心职责 | 产物 |
|---|---|---|---|
| 表 | 系统内核与规则管理员 | 存储输入、规则配置、计算结果和明细 | 输入表、规则表、结果表 |
| 插件 | 规则管理员与实施人员 | 封装可复用的复杂业务函数，降低公式配置难度 | 函数插件、字段校验器、结果处理器 |
| 工作流 | 绩效操作员 | 将导入、校验、计算、汇总、审核和导出编排成可执行流程 | 可执行的绩效核算流程 |

设计原则：表是唯一事实来源；插件不直接替代规则表，而是向规则表提供可调用函数；工作流不承载具体计算公式，而是负责组织各项任务的执行顺序、范围与异常处理。

### 4.2 计算流程

```text
导入或录入输入数据
        ↓
工作流执行数据校验与预处理
        ↓
加载绩效规则表
        ↓
校验字段、数据类型与规则完整性
        ↓
匹配适用规则
        ↓
执行内置函数或插件函数计算
        ↓
应用封顶、保底、扣减等限制
        ↓
工作流汇总、校验并输出个人分项结果、总结果与计算明细
```

### 4.2.1 Function 字段定义

底层记录的 `Function` 字段以 JSON 对象保存执行意图，内核读取该对象后调用受控执行器。该字段**不保存也不直接执行** Python、JavaScript 或其他任意源码。

MVP 的函数引用格式如下：

```json
{
  "kind": "registered",
  "name": "teaching_performance",
  "version": "1.0.0"
}
```

| 字段 | 必填 | 含义 |
|---|---:|---|
| `kind` | 是 | 函数类型。MVP 仅支持 `registered`，即调用内核已注册的函数。 |
| `name` | 是 | 函数稳定名称，例如 `teaching_performance`。 |
| `version` | 是 | 函数版本；计算任务冻结后用于精确追溯调用版本。 |

例如，课时绩效记录的 `Input` 为课时数、课程系数和课时单价，`Function` 引用 `teaching_performance@1.0.0`，内核将其解析为对应 Python 业务函数并保存其 `Output`。

后续可在同一 JSON 模型中增加 `expression`（受限公式语言）和 `plugin`（插件函数）类型，但不得将可执行源码直接放入记录字段。这样可保证函数白名单、参数校验、版本冻结、错误追踪和未来跨语言内核迁移的可行性。

### 4.3 插件模型

插件用于封装原本需要在规则表中反复编写的复杂函数。它将业务逻辑以清晰的输入参数和输出结果暴露给规则配置人员调用，避免操作员直接维护冗长、易错的表达式。

#### 插件能力

- 提供可复用计算函数，例如作者排序系数、课程类别系数、成果等级换算；
- 提供数据标准化能力，例如职称名称映射、课程分类映射；
- 提供输入校验能力，例如检查课时是否超出合理范围；
- 提供结果后处理能力，例如分项金额取整、封顶、保底和税前汇总；
- 提供函数说明、参数定义、示例和版本信息。

#### 插件调用示例

| 插件函数 | 输入参数 | 输出 | 规则表示例 |
|---|---|---|---|
| `course_coefficient` | 课程类型、课程级别 | 课程系数 | `课时数 * course_coefficient(课程类型, 课程级别) * 课时单价` |
| `author_ratio` | 作者排序、作者总数 | 作者系数 | `基础金额 * author_ratio(作者排序, 作者总数)` |
| `cap_amount` | 原始金额、上限 | 封顶金额 | `cap_amount(计算结果, 30000)` |
| `paper_score` | 论文等级、收录类型 | 论文积分 | `paper_score(论文等级, 收录类型)` |

#### 插件约束

- 插件必须定义名称、版本、输入参数、输出类型和错误说明；
- 插件函数应保持确定性：相同输入和相同插件版本必须得到相同输出；
- 插件升级不得改变历史计算结果；历史计算必须关联当时使用的插件版本；
- 插件执行日志应记录函数名称、版本、输入摘要、输出和异常信息；
- 插件不能绕过表结构直接修改历史输入或结果。

### 4.4 工作流模型

工作流面向绩效操作员，将一次绩效核算中的多个业务动作组织为可重复执行的流程。操作员只需按流程选择周期、范围和数据源，无需理解每条规则的计算细节。

#### MVP 标准工作流

| 顺序 | 工作流节点 | 操作员动作 | 系统执行内容 | 输出 |
|---:|---|---|---|---|
| 1 | 创建计算批次 | 选择年度、学期或考核周期 | 创建计算任务和结果版本 | 计算批次 |
| 2 | 导入数据 | 上传人员及业务数据 | 字段映射、格式校验、去重 | 输入记录 |
| 3 | 数据校验 | 查看并处理异常 | 校验必填项、关联关系和数据范围 | 异常清单 |
| 4 | 执行计算 | 确认计算范围 | 匹配规则并调用内置或插件函数 | 分项结果 |
| 5 | 汇总结果 | 发起汇总 | 汇总教学、科研、管理、奖励和扣减项 | 绩效总额 |
| 6 | 结果复核 | 查看异常及抽查明细 | 检查计算状态、规则命中和结果差异 | 待确认结果 |
| 7 | 发布或导出 | 确认结果版本 | 冻结结果并导出汇总、明细和异常数据 | 正式结果 |

#### 工作流能力

- 配置节点顺序与节点启停；
- 在节点间传递计算周期、组织范围、人员范围和结果版本；
- 支持节点失败、跳过、重试和回退；
- 支持在计算前或计算后增加人工复核节点；
- 为每次执行保留任务状态、操作人、时间和日志；
- 支持按学院、人员范围或指标分类发起局部工作流。

## 5. 规则表设计

### 5.1 规则表定位

规则表是系统的核心配置载体。一行规则代表一个可执行的绩效计算单元。

管理员通过维护规则表定义：

- 计算什么指标；
- 需要哪些输入字段；
- 满足什么条件时生效；
- 使用什么公式计算；
- 计算结果写入哪个输出字段；
- 是否存在封顶、保底或扣减规则。

### 5.2 规则表字段

| 字段 | 必填 | 说明 | 示例 |
|---|---:|---|---|
| 规则编号 | 是 | 规则唯一标识 | `TEACH_001` |
| 规则名称 | 是 | 规则的可读名称 | 本科教学课时绩效 |
| 指标分类 | 是 | 教学、科研、管理、奖励等 | 教学 |
| 输入字段 | 是 | 本规则依赖的字段列表 | `课时数,课程系数` |
| 生效条件 | 否 | 满足条件才执行 | `岗位类型 == "教师"` |
| 计算函数 | 是 | 可执行公式 | `课时数 * 课程系数 * 课时单价` |
| 输出字段 | 是 | 结果写入的字段 | 教学绩效 |
| 结果类型 | 是 | 金额、积分、比例等 | 金额 |
| 封顶规则 | 否 | 输出最大值 | `min(计算结果, 30000)` |
| 优先级 | 否 | 多规则命中时的执行顺序 | `100` |
| 生效开始日期 | 否 | 规则启用日期 | `2026-01-01` |
| 生效结束日期 | 否 | 规则截止日期 | `2026-12-31` |
| 状态 | 是 | 启用或停用 | 启用 |
| 备注 | 否 | 政策来源或说明 | 校发〔2026〕12号 |

### 5.3 示例规则

| 规则编号 | 规则名称 | 生效条件 | 计算函数 | 输出字段 |
|---|---|---|---|---|
| TEACH_001 | 本科教学课时绩效 | `岗位类型 == "教师"` | `课时数 * 课程系数 * 课时单价` | 教学绩效 |
| RESEARCH_001 | A类论文绩效 | `论文等级 == "A"` | `基础金额 * 作者系数` | 科研绩效 |
| POST_001 | 管理岗位绩效 | `岗位等级 != ""` | `岗位月标准 * 任职月份` | 管理绩效 |
| TOTAL_001 | 总绩效汇总 | `true` | `教学绩效 + 科研绩效 + 管理绩效` | 绩效总额 |

### 5.4 跨表链接定义

跨表链接用于使一条记录能够读取另一张表中的数据或等待另一条记录完成执行。链接是底层表记录的一部分，而非仅存在于可视化工作流中的连线。

第一阶段不提供复杂查询语言或任意动态关联，而采用可校验的显式链接。

#### 链接结构

| 字段 | 必填 | 说明 | 示例 |
|---|---:|---|---|
| 链接 ID | 是 | 链接唯一标识 | `link_001` |
| 源表 / 源记录 | 是 | 发起引用的记录 | `绩效汇总 / total_001` |
| 链接类型 | 是 | `data` 或 `execution` | `execution` |
| 目标表 | 是 | 被引用记录所在表 | `科研绩效` |
| 目标记录 ID | 是 | 被引用记录的稳定 ID | `research_023` |
| 目标字段或输出路径 | 否 | 读取目标记录中的字段或输出值 | `output.amount` |
| 缺失策略 | 是 | 目标不存在时的处理方式 | `fail` |
| 版本策略 | 是 | 使用目标的当前有效版本或冻结版本 | `pinned` |

#### 链接类型与语义

| 类型 | 用途 | 执行语义 |
|---|---|---|
| 数据链接 `data` | 读取另一记录中的已存在数据 | 仅解析目标字段，不改变当前记录的调度顺序；目标缺失或字段不可读时，当前记录进入异常状态 |
| 执行依赖 `execution` | 当前记录依赖目标记录的计算结果 | 当前记录必须等待目标记录成功完成且输出已提交后才可执行；目标失败、取消或不存在时，当前记录不可执行并记录依赖异常 |

例如，“综合绩效汇总”记录通过两个 `execution` 链接依赖教学绩效和科研绩效记录，并读取两者的 `output.amount`；这些依赖同时也是工作流画布中可视化连线的底层来源。

#### 第一阶段链接约束

- 目标记录必须使用稳定记录 ID 定位，不支持按名称或模糊条件查找；
- 输入解析时，内核先读取普通输入，再解析数据链接和执行依赖的输出引用；
- 执行依赖构成有向图，创建或修改链接时必须检测循环依赖；
- 一个记录仅在全部执行依赖成功后进入“可执行”状态；
- 数据链接不会自动触发目标记录执行，避免隐式调度行为；
- `pinned` 链接在计算批次创建时冻结目标记录和输出版本，保证历史结果可追溯；
- 目标记录、目标字段或目标版本不存在时，默认采用 `fail` 策略，将当前记录标记为“依赖异常”；
- 当前最小实现仅支持指定记录的局部重载：清除该记录的输出和错误后重新执行，不自动影响其他记录或下游结果。

#### 第一阶段不支持的能力

- 跨表模糊查询、聚合查询和动态条件选取；
- 隐式双向关系；
- 自动推断链接关系；
- 在运行过程中无记录地修改链接目标；
- 允许循环依赖或不受约束的递归执行。

## 6. 功能需求

### 6.1 插件管理

#### 功能说明

管理员或实施人员可安装、启用和维护计算插件；规则管理员在编辑规则时可选择并调用已启用的插件函数。

#### MVP 功能

- 查看已安装插件及其版本、状态和说明；
- 查看每个插件提供的函数、参数、返回类型和调用示例；
- 启用或停用插件；
- 在规则编辑器中插入插件函数；
- 在规则保存前验证插件函数的参数数量和类型；
- 查看插件被哪些规则和计算批次使用。

#### 验收标准

- 规则管理员无需了解插件内部实现，即可按函数说明完成调用；
- 停用中的插件不可被新规则引用；
- 对已被历史计算使用的插件，系统可查看其对应版本；
- 插件函数执行失败时，系统能定位到人员、规则、插件和错误原因。

### 6.2 规则管理

#### 功能说明

管理员可创建、编辑、复制、启用、停用和导入绩效规则。

#### MVP 功能

- 新建规则；
- 编辑规则字段；
- 批量导入规则表；
- 导出规则表；
- 启用或停用规则；
- 复制已有规则作为新版本；
- 校验公式是否合法；
- 展示规则生效范围和版本信息。

#### 验收标准

- 管理员可在不修改代码的情况下新增或修改计算规则；
- 系统可识别公式中引用的输入字段；
- 当字段不存在、公式错误或条件不合法时，系统给出明确提示；
- 已用于历史计算的规则不可直接覆盖，应保留历史版本。

### 6.3 输入数据管理

#### 功能说明

管理员可导入或手动维护人员与绩效原始数据。

#### MVP 输入数据类型

| 数据类型 | 示例字段 |
|---|---|
| 人员基础信息 | 工号、姓名、学院、岗位、职级 |
| 教学数据 | 课程名称、课时数、课程类型、课程系数 |
| 科研数据 | 成果名称、成果类型、成果等级、作者排序 |
| 管理数据 | 岗位等级、任职月份、岗位系数 |
| 其他数据 | 获奖等级、社会服务时长、扣减项 |

#### 验收标准

- 支持 Excel 或 CSV 导入；
- 支持按工号识别人员；
- 系统校验必填字段、数据类型和重复数据；
- 导入失败时提供错误行及原因；
- 原始导入数据可追溯，不被计算结果覆盖。

### 6.4 绩效计算

#### 功能说明

系统根据计算周期、人员数据和启用规则，批量计算绩效结果。

#### MVP 功能

- 选择计算周期；
- 选择计算范围，例如学院、人员或岗位；
- 执行批量计算；
- 支持重新计算；
- 生成计算任务记录；
- 展示任务状态：待执行、计算中、成功、失败；
- 对缺失字段、无匹配规则、计算异常给出提示。

#### 验收标准

- 同一输入与同一规则版本下，多次计算结果一致；
- 系统可记录每次计算所用规则版本；
- 单条数据异常不会阻塞其他人员的正常计算；
- 可查看异常人员及异常原因。

### 6.5 结果查看与追溯

#### 功能说明

系统按人员展示绩效总额、分项结果及每笔结果的计算来源。

#### 结果字段

| 字段 | 说明 |
|---|---|
| 工号 | 人员唯一标识 |
| 姓名 | 人员姓名 |
| 学院 | 所属组织 |
| 计算周期 | 绩效所属周期 |
| 教学绩效 | 教学模块计算结果 |
| 科研绩效 | 科研模块计算结果 |
| 管理绩效 | 管理模块计算结果 |
| 奖励或扣减 | 其他调整项 |
| 绩效总额 | 汇总结果 |
| 计算状态 | 正常、异常、待补充 |
| 计算时间 | 本次计算完成时间 |

#### 明细追溯内容

- 使用的规则编号及规则版本；
- 命中的生效条件；
- 原始输入字段和值；
- 执行的计算公式；
- 中间计算结果；
- 封顶、扣减或调整过程；
- 最终输出结果。

### 6.6 工作流中心

#### 功能说明

工作流中心为绩效操作员提供固定或可配置的核算操作路径，减少其直接接触规则、函数和底层数据的需要。

#### MVP 功能

- 选择标准绩效核算工作流；
- 创建、暂停、恢复和终止计算批次；
- 展示当前节点、执行状态、操作人和异常数量；
- 在数据校验、结果复核节点处理异常后继续执行；
- 支持从失败节点重试，避免重复导入或重复计算；
- 在发布节点冻结规则版本、插件版本、输入快照和结果快照。

#### 验收标准

- 操作员可在不编辑规则的情况下完成一次标准核算；
- 工作流可清晰展示当前批次停留的节点及下一步操作；
- 计算失败后可重试失败节点，不影响此前成功节点的结果；
- 已发布的结果可回溯到完整的工作流执行记录。

### 6.7 导出功能

#### MVP 导出内容

- 绩效汇总表；
- 个人绩效明细表；
- 异常数据清单；
- 当前规则表；
- 计算任务记录。

## 8. 业务规则

### 8.1 规则匹配

- 仅执行状态为“启用”的规则；
- 规则必须处于当前计算周期的生效日期范围内；
- 人员数据满足生效条件时，规则才可执行；
- 多条规则可同时命中，按优先级执行；
- 同一输出字段的多个结果默认累加；
- 如规则设置“覆盖模式”，高优先级规则可覆盖低优先级结果。

### 8.2 数据校验

- 工号必须唯一；
- 金额、课时数、系数等数值字段必须符合格式；
- 公式中引用的字段必须存在；
- 日期必须符合计算周期；
- 成果、课程等明细数据需关联到具体人员；
- 缺失必要输入时，该条结果标记为异常。

### 8.3 结果冻结

- 每次完成计算后生成一个结果版本；
- 历史结果、规则版本和原始输入不可被后续修改影响；
- 如需更正，需重新发起一次计算并产生新版本；
- 系统需保留历史版本供审计和比对。

## 12. 整体开发路线

本路线是逻辑上的能力演进，不要求某一阶段全部完成后才能进入下一阶段。特别是结果恢复所需的最小持久化能力、版本冻结以及执行边界，应在内核阶段预先设计。

```text
第一阶段：最小内核
    │
    ├── 表与记录
    ├── 输入、函数、输出
    ├── 单线程执行循环
    ├── 状态管理
    └── 局部重载
           │
           ▼
第二阶段：执行能力扩展
    │
    ├── Python 业务执行器
    ├── 插件注册
    ├── 工作流可视化
    └── 执行结果与错误追踪
           │
           ▼
第三阶段：系统管理能力
    │
    ├── 身份与权限
    ├── 信息管理
    ├── 日志与审计
    └── 配置与版本管理
           │
           ▼
第四阶段：稳定运行与演进
    │
    ├── 异常恢复
    ├── 运行监控
    ├── 性能优化
    └── Go 内核迁移
```

### 12.1 第一阶段：最小内核

第一阶段只验证系统的执行语义，不追求完整界面、权限体系或外部系统集成。

#### 表与记录

每一条记录包含三个业务核心字段：

| 字段 | 职责 |
|---|---|
| Input | 描述函数需要的输入 |
| Function | 以受控 JSON 描述指定执行逻辑和版本 |
| Output | 保存执行结果或结果引用 |

记录还必须具备记录 ID、状态、依赖关系、创建时间、更新时间和版本等元数据。这些元数据不改变三字段模型，而是用于管理记录的执行生命周期。

#### 单线程执行循环

第一版内核采用单线程循环，执行流程保持可预测：

1. 按创建时间找到一条处于待执行状态的记录；
2. 解析该记录的输入与 Function JSON；
3. 调用已注册的对应函数；
4. 接收输出并以原子方式提交结果，或保存错误信息；
5. 更新状态与尝试次数，继续处理下一条记录。

单线程并非最终性能方案，而是用最小实现明确调度、状态转换、失败处理与结果提交的语义，为后续并发执行或 Go 内核迁移保留稳定边界。

#### 状态与局部重载

当前最小实现支持：`待执行`、`执行中`、`成功` 和 `失败` 四种状态，并为每次执行记录尝试次数和失败信息。

- 暂不实现插队；待执行记录严格按创建时间顺序在单线程中运行；
- 仅支持局部重载：重载指定记录会清除该记录的输出和错误，将其恢复为待执行；
- `retry_record` 在局部重载后立即执行该记录；重试失败时必须返回最新错误信息；
- 局部重载不影响其他表、其他记录或任何潜在下游记录；
- 单条记录失败不得阻塞其他待执行记录继续执行。

#### 真实闭环验证

第一阶段以一个真实但小规模的绩效计算场景验收：

```text
teaching_rules 表
   ├── 课时绩效：成功
   └── 精品课程奖励：失败（无效课程等级）

research_rules 表
   └── 科研绩效：成功

仅局部重载并重试“精品课程奖励”
   └── 返回同一条规则的错误信息
```

验收标准是：三个不同规则分布在两个表中，两条规则成功并保存输出，一条规则失败并保存错误；重试失败规则后，系统再次提示该记录的错误，且两条成功规则不被重新执行。

### 12.2 第二阶段：执行能力扩展

第二阶段围绕已验证的内核建立可使用性，而不重新实现调度机制。

- **Python 业务执行器**：将具体业务逻辑放在 Python 中，并按统一执行契约由内核调用；
- **插件注册**：将复杂、可复用的业务函数注册为插件函数，供规则表调用；
- **工作流可视化**：通过拖拽、连线和参数配置编辑表记录及其链接；
- **结果与错误追踪**：展示函数调用、插件版本、输入摘要、输出、状态和异常堆栈。

可视化工作流不是底层数据的唯一来源。界面修改应生成或更新表记录和链接，其他工具同样能够读取、处理和导入这些底层数据。

### 12.3 第三阶段：系统管理能力

当系统开始服务真实用户后，逐步建设身份认证、角色权限、信息管理、日志审计以及配置和版本管理。

权限虽在此阶段完整实现，但内核阶段必须保留最小安全边界：

- 仅内核可变更记录执行状态和提交执行结果；
- 执行器和插件仅能通过受控接口读取和写入被授权数据；
- 外部业务代码不得绕过内核直接修改历史结果；
- 对规则、链接、重载和发布等关键操作保留可审计事件。

### 12.4 第四阶段：稳定运行与演进

在核心语义和业务模型稳定后，扩展异常恢复、运行监控、性能优化，并评估将执行内核迁移至 Go。

迁移目标是提升执行效率和运行稳定性，不改变“表记录、显式链接、函数调用、状态机和结果版本”的既定业务语义。

## 14. 风险与应对

| 风险 | 说明 | 应对方式 |
|---|---|---|
| 规则过于复杂 | 不同学院规则表达差异大 | 先支持高频规则，逐步扩展函数库 |
| 公式配置错误 | 管理员可能误填公式 | 提供校验、试算与规则预览 |
| 原始数据质量差 | 导入字段缺失、格式不统一 | 提供模板、字段映射和错误清单 |
| 历史结果争议 | 规则变动后难以解释旧结果 | 冻结规则、输入和计算明细 |
| 权限边界不清 | 绩效数据具有敏感性 | 采用按角色和学院的数据权限 |

## 15. 数据 MVP：统一成果与审核

教学工作量、论文、项目、经费、社会服务和人才培养等数据先统一为成果记录，至少包含教师、类型、等级、时间、状态和来源原始数据。系统支持教务、科研来源的接口导入与教师手工申报；所有记录先进入院系审核，审核通过后才可作为规则表的 Input 参与绩效计算。当前 `ADMIN` 暂承担院系审核角色，后续按院系范围拆分权限。

## 16. 核心价值

该系统的核心不是“替高校写一套固定绩效规则”，而是提供一个可配置的绩效计算内核。

通过统一的“输入—函数—输出”模型，学校可以把不断变化的绩效政策转化为可维护、可执行、可解释的规则表；管理员能够快速完成核算，教职工能够理解结果来源，管理部门能够保留完整的审计链路。
