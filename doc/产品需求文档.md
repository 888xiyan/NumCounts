# 高校绩效计算系统：MVP 产品需求文档

## 1. 产品概述

### 1.1 产品名称

高校绩效计算系统（暂定名：NumCounts）

### 1.2 产品背景

高校绩效管理规则通常复杂且变化频繁，涉及教学、科研、管理、社会服务、奖励等多个维度。不同学院、岗位、职级、年度或考核周期往往适用不同的计算方式。

传统以手工表格处理绩效的方式存在以下问题：

- 规则分散在多个文件中，维护成本高；
- 公式容易被误改，计算结果难以追溯；
- 规则变更后需要重复修改大量表格；
- 数据录入、校验、计算和发放之间缺少统一链路；
- 教职工难以理解个人绩效结果的来源。

本系统以“单张规则表”为核心，通过统一的输入、函数和输出模型，实现可配置、可计算、可追溯的高校绩效核算。

在此基础上，系统引入插件和工作流两层能力：插件将复杂、重复的计算逻辑封装为业务函数，工作流则面向操作员编排数据导入、计算、校验、汇总和导出等步骤。无论插件或工作流如何扩展，底层规则、输入和结果仍以表结构保存和追溯。

### 1.3 产品定位

一个面向高校绩效管理员和组内成员的轻量化、可配置绩效计算工具：管理员负责配置和正式核算，成员使用已发布能力查看、导出个人绩效并提出申诉。

系统不预设某一所高校的固定规则，而是提供规则配置与计算内核，使管理人员能通过维护表格适配本校、本学院或本年度的绩效政策。

### 1.4 业务决策状态说明

本文中的业务要求按以下状态标注：

- **【已确定】**：已由当前业务梳理明确，后续设计和实现应遵守。
- **【待确定】**：目前缺少业务决策。相关设计不得擅自视为最终口径；实现前应由业务负责人确认。
- 未加状态标记的原有内容属于产品构想或MVP建议，不自动视为已确定业务规则。

本次确认的业务基线如下：

| 主题 | 状态 | 业务口径 |
|---|---|---|
| 插件管理 | 【已确定】 | 插件用于帮助管理员快速编写工作流；仅管理员可设置插件版本和修改插件。 |
| 工作流管理 | 【已确定】 | 管理员制定绩效审核工作流，供组内成员使用。 |
| 管理员职责 | 【已确定】 | 编写和统一工作流及插件，执行基础绩效计算，审核成员提交的特殊绩效计算或申诉。 |
| 成员职责 | 【已确定】 | 查看、导出个人绩效，提交绩效申诉；可使用所有插件和工作流，但使用结果只能暂存和导出，不产生正式绩效落地或效益。 |
| 正式计算留存 | 【已确定】 | 管理员执行的计算应实际落库。 |
| 函数留存 | 【已确定】 | 正式计算的持久化内容应保存当次实际使用的函数本体，不能只保存字段和版本标识。 |
| 特殊绩效与申诉 | 【已确定】 | 面向需要材料和审批的复杂绩效事项；草稿可编辑、提交后冻结，管理员在三天内处理/复核，通过后经专用插件生成可核算成果并由重新核算创建新结果版本。通知仅预留接口。 |
| 暂存规则 | 【待确定】 | 成员试算暂存的保留期限、可见范围、清理方式以及是否允许管理员查看尚未确定。 |
| 函数快照实现 | 【待确定】 | 函数本体的存储格式、存储位置、依赖封存方式和历史复现策略尚未确定；须在受控执行边界内设计。 |

## 2. 产品目标

### 2.1 核心目标

- 用一张规则表描述绝大多数绩效计算规则；
- 支持管理员无需编程即可调整绩效计算逻辑；
- 自动生成个人绩效总额、分项结果及计算明细；
- 支持规则、输入数据和计算结果全流程追溯；
- 在规则频繁变化的场景下，降低维护和核算成本。

### 2.2 MVP 成功标准

- 管理员可创建或导入一份绩效规则表；
- 管理员可导入教师或员工的绩效原始数据；
- 系统可按规则自动计算绩效结果；
- 每条结果可查看使用了哪些输入、规则和公式；
- 支持导出最终结果及计算明细。

### 2.3 非目标

MVP 阶段暂不覆盖：

- 工资发放或财务系统直连；
- 多级审批流；
- 移动端应用；
- 复杂组织权限体系；
- 自动采集科研、教务或人事系统数据；
- 大规模跨校数据协同。

## 3. 用户与使用场景

### 3.1 目标用户

| 用户角色 | 主要职责 | 核心诉求 |
|---|---|---|
| 管理员 | 编写和统一插件、工作流；执行基础绩效计算；审核特殊绩效计算或申诉 | 统一计算口径，形成正式且可追溯的绩效结果 |
| 组内成员 | 使用管理员发布的插件和工作流；查看、导出个人绩效；提交申诉 | 自助核对个人绩效并提出异议 |

**【待确定】**管理员是否细分为系统管理员、绩效管理员、学院管理员等角色，以及各角色的组织范围和相互授权关系。

### 3.2 典型使用场景

#### 场景一：年度教学绩效核算

管理员导入教师课时、课程类别和课程系数，配置教学绩效公式：

`教学绩效 = 课时数 × 课程系数 × 课时单价`

系统批量计算每位教师的教学绩效。

#### 场景二：科研成果积分计算

管理员导入论文、项目、专利和获奖数据，根据成果等级、作者排序及学院政策计算科研绩效。

#### 场景三：规则调整后重新测算

学校调整某类课程的系数，管理员仅修改规则表中的函数或条件，重新执行计算，无需重做全部原始表格。

#### 场景四：个人结果核查

教师查看个人结果，系统展示其原始输入、命中的规则、执行公式和最终分项金额。

## 4. 核心产品模型

### 4.1 总体模型

系统由三类核心数据组成：

`输入数据 + 规则函数 + 输出结果`

| 模块 | 含义 | 示例 |
|---|---|---|
| 输入 | 用于计算的原始业务数据 | 课时数、论文等级、项目经费、岗位等级 |
| 函数 | 绩效计算公式、判断条件和限制规则 | `课时数 × 系数 × 单价` |
| 输出 | 系统计算得到的结果 | 教学绩效、科研绩效、总绩效 |

系统通过“表、插件、工作流”三层协同工作：

| 层级 | 面向对象 | 核心职责 | 产物 |
|---|---|---|---|
| 表 | 系统内核与规则管理员 | 存储输入、规则配置、计算结果和明细 | 输入表、规则表、结果表 |
| 插件 | 规则管理员与实施人员 | 封装可复用的复杂业务函数，降低公式配置难度 | 函数插件、字段校验器、结果处理器 |
| 工作流 | 绩效操作员 | 将导入、校验、计算、汇总、审核和导出编排成可执行流程 | 可执行的绩效核算流程 |

设计原则：表是唯一事实来源；插件不直接替代规则表，而是向规则表提供可调用函数；工作流不承载具体计算公式，而是负责组织各项任务的执行顺序、范围与异常处理。

### 4.2 计算流程

```text
导入或录入输入数据
        ↓
工作流执行数据校验与预处理
        ↓
加载绩效规则表
        ↓
校验字段、数据类型与规则完整性
        ↓
匹配适用规则
        ↓
执行内置函数或插件函数计算
        ↓
应用封顶、保底、扣减等限制
        ↓
工作流汇总、校验并输出个人分项结果、总结果与计算明细
```

### 4.2.1 Function 字段定义

底层记录的 `Function` 字段以 JSON 对象描述执行意图，内核通过受控执行器完成计算。**【已确定】正式计算必须保存实际执行的函数本体**，使历史记录具备函数内容层面的追溯依据；只保存函数名称、字段和版本号不足以满足要求。函数快照须与输入、输出及插件/工作流版本关联。

函数快照的具体序列化格式、保存位置、依赖封存和复现机制为**【待确定】**。函数本体留存不构成任意代码执行授权；函数仍须经过受控登记、白名单校验和执行器隔离。

MVP 的函数引用格式如下：

```json
{
  "kind": "registered",
  "name": "teaching_performance",
  "version": "1.0.0"
}
```

| 字段 | 必填 | 含义 |
|---|---:|---|
| `kind` | 是 | 函数类型。当前支持 `registered`、`external` 与 `plugin`；插件仅引用已启用的版本化规则插件。 |
| `name` | 是 | 函数稳定名称，例如 `teaching_performance`。 |
| `version` | 是 | 函数版本；计算任务冻结后用于精确追溯调用版本。 |

例如，课时绩效记录的 `Input` 为课时数、课程系数和课时单价，`Function` 描述受控函数，正式计算记录同时保存该次解析后实际使用的函数本体快照及 `Output`。

后续可在同一 JSON 模型中增加 `expression`（受限公式语言），但不得将未经校验的可执行源码直接执行。函数本体快照的物理存储形式待定；业务上要求正式计算可追溯到当次实际函数内容。

### 4.3 插件模型

插件用于封装原本需要在规则表中反复编写的复杂函数。它将业务逻辑以清晰的输入参数和输出结果暴露给规则配置人员调用，避免操作员直接维护冗长、易错的表达式。

#### 插件能力

- 提供可复用计算函数，例如作者排序系数、课程类别系数、成果等级换算；
- 提供数据标准化能力，例如职称名称映射、课程分类映射；
- 提供输入校验能力，例如检查课时是否超出合理范围；
- 提供结果后处理能力，例如分项金额取整、封顶、保底和税前汇总；
- 提供函数说明、参数定义、示例和版本信息。

#### 插件调用示例

| 插件函数 | 输入参数 | 输出 | 规则表示例 |
|---|---|---|---|
| `course_coefficient` | 课程类型、课程级别 | 课程系数 | `课时数 * course_coefficient(课程类型, 课程级别) * 课时单价` |
| `author_ratio` | 作者排序、作者总数 | 作者系数 | `基础金额 * author_ratio(作者排序, 作者总数)` |
| `cap_amount` | 原始金额、上限 | 封顶金额 | `cap_amount(计算结果, 30000)` |
| `paper_score` | 论文等级、收录类型 | 论文积分 | `paper_score(论文等级, 收录类型)` |

#### 插件约束

- 插件必须定义名称、版本、输入参数、输出类型和错误说明；
- 插件函数应保持确定性：相同输入和相同插件版本必须得到相同输出；
- 插件升级不得改变历史计算结果；历史计算必须关联当时使用的插件版本；
- 插件执行日志应记录函数名称、版本、输入摘要、输出和异常信息；
- 插件不能绕过表结构直接修改历史输入或结果。
- **【已确定】只有管理员可以创建、修改插件及设置插件版本；成员只能使用管理员提供的插件。**
- 插件版本发布后的生命周期规则（启停、审批、生效和回滚）为**【待确定】**。

### 4.4 工作流模型

工作流面向绩效操作员，将一次绩效核算中的多个业务动作组织为可重复执行的流程。操作员只需按流程选择周期、范围和数据源，无需理解每条规则的计算细节。

**【已确定】**管理员制定绩效审核工作流并供组内成员使用。成员运行结果只能暂存和导出，不能形成正式绩效结果或业务效益；管理员执行的正式计算必须落库。成员提交某次试算供管理员审核的方式为**【待确定】**。

#### MVP 标准工作流

| 顺序 | 工作流节点 | 操作员动作 | 系统执行内容 | 输出 |
|---:|---|---|---|---|
| 1 | 创建计算批次 | 管理员选择年度、学期或考核周期 | 创建正式计算任务和结果版本；成员运行创建非正式暂存 | 管理员计算批次或成员暂存 |
| 2 | 导入数据 | 上传人员及业务数据 | 字段映射、格式校验、去重 | 输入记录 |
| 3 | 数据校验 | 查看并处理异常 | 校验必填项、关联关系和数据范围 | 异常清单 |
| 4 | 执行计算 | 确认计算范围 | 匹配规则并调用内置或插件函数 | 分项结果 |
| 5 | 汇总结果 | 发起汇总 | 汇总教学、科研、管理、奖励和扣减项 | 绩效总额 |
| 6 | 结果复核 | 查看异常及抽查明细 | 检查计算状态、规则命中和结果差异 | 待确认结果 |
| 7 | 发布或导出 | 管理员确认结果版本；成员导出个人结果 | 管理员正式计算落库并冻结结果；成员仅导出暂存结果 | 正式结果或成员导出文件 |

#### 工作流能力

- 配置节点顺序与节点启停；
- 在节点间传递计算周期、组织范围、人员范围和结果版本；
- 支持节点失败、跳过、重试和回退；
- 支持在计算前或计算后增加人工复核节点；
- 为每次执行保留任务状态、操作人、时间和日志；
- 支持按学院、人员范围或指标分类发起局部工作流。

## 5. 规则表设计

### 5.1 规则表定位

规则表是系统的核心配置载体。一行规则代表一个可执行的绩效计算单元。

管理员通过维护规则表定义：

- 计算什么指标；
- 需要哪些输入字段；
- 满足什么条件时生效；
- 使用什么公式计算；
- 计算结果写入哪个输出字段；
- 是否存在封顶、保底或扣减规则。

### 5.2 规则表字段

| 字段 | 必填 | 说明 | 示例 |
|---|---:|---|---|
| 规则编号 | 是 | 规则唯一标识 | `TEACH_001` |
| 规则名称 | 是 | 规则的可读名称 | 本科教学课时绩效 |
| 指标分类 | 是 | 教学、科研、管理、奖励等 | 教学 |
| 输入字段 | 是 | 本规则依赖的字段列表 | `课时数,课程系数` |
| 生效条件 | 否 | 满足条件才执行 | `岗位类型 == "教师"` |
| 计算函数 | 是 | 可执行公式 | `课时数 * 课程系数 * 课时单价` |
| 输出字段 | 是 | 结果写入的字段 | 教学绩效 |
| 结果类型 | 是 | 金额、积分、比例等 | 金额 |
| 封顶规则 | 否 | 输出最大值 | `min(计算结果, 30000)` |
| 优先级 | 否 | 多规则命中时的执行顺序 | `100` |
| 生效开始日期 | 否 | 规则启用日期 | `2026-01-01` |
| 生效结束日期 | 否 | 规则截止日期 | `2026-12-31` |
| 状态 | 是 | 启用或停用 | 启用 |
| 备注 | 否 | 政策来源或说明 | 校发〔2026〕12号 |

### 5.3 示例规则

| 规则编号 | 规则名称 | 生效条件 | 计算函数 | 输出字段 |
|---|---|---|---|---|
| TEACH_001 | 本科教学课时绩效 | `岗位类型 == "教师"` | `课时数 * 课程系数 * 课时单价` | 教学绩效 |
| RESEARCH_001 | A类论文绩效 | `论文等级 == "A"` | `基础金额 * 作者系数` | 科研绩效 |
| POST_001 | 管理岗位绩效 | `岗位等级 != ""` | `岗位月标准 * 任职月份` | 管理绩效 |
| TOTAL_001 | 总绩效汇总 | `true` | `教学绩效 + 科研绩效 + 管理绩效` | 绩效总额 |

### 5.4 跨表链接定义

跨表链接用于使一条记录能够读取另一张表中的数据或等待另一条记录完成执行。链接是底层表记录的一部分，而非仅存在于可视化工作流中的连线。

第一阶段不提供复杂查询语言或任意动态关联，而采用可校验的显式链接。

#### 链接结构

| 字段 | 必填 | 说明 | 示例 |
|---|---:|---|---|
| 链接 ID | 是 | 链接唯一标识 | `link_001` |
| 源表 / 源记录 | 是 | 发起引用的记录 | `绩效汇总 / total_001` |
| 链接类型 | 是 | `data` 或 `execution` | `execution` |
| 目标表 | 是 | 被引用记录所在表 | `科研绩效` |
| 目标记录 ID | 是 | 被引用记录的稳定 ID | `research_023` |
| 目标字段或输出路径 | 否 | 读取目标记录中的字段或输出值 | `output.amount` |
| 缺失策略 | 是 | 目标不存在时的处理方式 | `fail` |
| 版本策略 | 是 | 使用目标的当前有效版本或冻结版本 | `pinned` |

#### 链接类型与语义

| 类型 | 用途 | 执行语义 |
|---|---|---|
| 数据链接 `data` | 读取另一记录中的已存在数据 | 仅解析目标字段，不改变当前记录的调度顺序；目标缺失或字段不可读时，当前记录进入异常状态 |
| 执行依赖 `execution` | 当前记录依赖目标记录的计算结果 | 当前记录必须等待目标记录成功完成且输出已提交后才可执行；目标失败、取消或不存在时，当前记录不可执行并记录依赖异常 |

例如，“综合绩效汇总”记录通过两个 `execution` 链接依赖教学绩效和科研绩效记录，并读取两者的 `output.amount`；这些依赖同时也是工作流画布中可视化连线的底层来源。

#### 第一阶段链接约束

- 目标记录必须使用稳定记录 ID 定位，不支持按名称或模糊条件查找；
- 输入解析时，内核先读取普通输入，再解析数据链接和执行依赖的输出引用；
- 执行依赖构成有向图，创建或修改链接时必须检测循环依赖；
- 一个记录仅在全部执行依赖成功后进入“可执行”状态；
- 数据链接不会自动触发目标记录执行，避免隐式调度行为；
- `pinned` 链接在计算批次创建时冻结目标记录和输出版本，保证历史结果可追溯；
- 目标记录、目标字段或目标版本不存在时，默认采用 `fail` 策略，将当前记录标记为“依赖异常”；
- 当前最小实现仅支持指定记录的局部重载：清除该记录的输出和错误后重新执行，不自动影响其他记录或下游结果。

#### 第一阶段不支持的能力

- 跨表模糊查询、聚合查询和动态条件选取；
- 隐式双向关系；
- 自动推断链接关系；
- 在运行过程中无记录地修改链接目标；
- 允许循环依赖或不受约束的递归执行。

## 6. 功能需求

本章功能需求应按第 1.4 节的状态标记理解。管理员正式计算和成员个人试算必须区分持久化范围：前者落库并参与正式绩效，后者仅暂存和导出。

### 6.1 插件管理

#### 功能说明

仅管理员可维护插件及设置插件版本；管理员和组内成员均可使用提供的插件。成员侧计算仅限个人暂存和导出。

#### MVP 功能

- 查看已安装插件及其版本、状态和说明；
- 查看每个插件提供的函数、参数、返回类型和调用示例；
- 管理员创建、修改插件并设置插件版本；
- 管理员编写或维护工作流时选择插件；
- 成员使用已提供的插件，不具备修改插件或设置版本的权限；
- 校验插件函数的参数和类型；
- 追溯插件被哪些工作流和正式计算使用。

#### 验收标准

- 规则管理员无需了解插件内部实现，即可按函数说明完成调用；
- 停用中的插件不可被新规则引用；
- 对已被历史计算使用的插件，系统可查看其对应版本；
- 插件函数执行失败时，系统能定位到人员、规则、插件和错误原因。

### 6.2 规则管理

#### 功能说明

管理员负责编写和统一绩效规则、插件及工作流；规则表的编辑和版本操作依照受控版本规则执行。

#### MVP 功能

- 新建规则；
- 编辑规则字段；
- 批量导入规则表；
- 导出规则表；
- 启用或停用规则；
- 复制已有规则作为新版本；
- 校验公式是否合法；
- 展示规则生效范围和版本信息。

#### 验收标准

- 管理员可在不修改代码的情况下新增或修改计算规则；
- 系统可识别公式中引用的输入字段；
- 当字段不存在、公式错误或条件不合法时，系统给出明确提示；
- 已用于历史计算的规则不可直接覆盖，应保留历史版本。

### 6.3 输入数据管理

#### 功能说明

管理员可导入或手动维护人员与绩效原始数据。

#### MVP 输入数据类型

| 数据类型 | 示例字段 |
|---|---|
| 人员基础信息 | 工号、姓名、学院、岗位、职级 |
| 教学数据 | 课程名称、课时数、课程类型、课程系数 |
| 科研数据 | 成果名称、成果类型、成果等级、作者排序 |
| 管理数据 | 岗位等级、任职月份、岗位系数 |
| 其他数据 | 获奖等级、社会服务时长、扣减项 |

#### 验收标准

- 支持 Excel 或 CSV 导入；
- 支持按工号识别人员；
- 系统校验必填字段、数据类型和重复数据；
- 导入失败时提供错误行及原因；
- 原始导入数据可追溯，不被计算结果覆盖。

### 6.4 绩效计算

#### 功能说明

系统根据计算周期、人员数据和规则进行计算。管理员发起的基础绩效计算属于正式计算并落库；成员侧计算属于非正式个人试算，只暂存和导出。

#### MVP 功能

- 选择计算周期；
- 选择计算范围，例如学院、人员或岗位；
- 执行批量计算；
- 支持重新计算；
- 管理员正式计算生成持久化计算任务及结果记录；
- 成员试算只暂存运行所需内容，不形成正式结果或绩效效益；
- 展示任务状态：待执行、计算中、成功、失败；
- 对缺失字段、无匹配规则、计算异常给出提示。

#### 验收标准

- 同一输入与同一规则版本下，多次计算结果一致；
- 系统可记录每次计算所用规则版本；
- 正式计算记录保存当次实际执行的函数本体；
- 成员试算与正式计算在状态、结果用途和访问范围上明确区分；
- 单条数据异常不会阻塞其他人员的正常计算；
- 可查看异常人员及异常原因。

### 6.5 结果查看与追溯

#### 功能说明

系统向成员展示并允许其导出本人绩效总额、分项结果和计算来源；管理员可查看正式结果并审核成员提交的特殊绩效计算或申诉。

#### 结果字段

| 字段 | 说明 |
|---|---|
| 工号 | 人员唯一标识 |
| 姓名 | 人员姓名 |
| 学院 | 所属组织 |
| 计算周期 | 绩效所属周期 |
| 教学绩效 | 教学模块计算结果 |
| 科研绩效 | 科研模块计算结果 |
| 管理绩效 | 管理模块计算结果 |
| 奖励或扣减 | 其他调整项 |
| 绩效总额 | 汇总结果 |
| 计算状态 | 正常、异常、待补充 |
| 计算时间 | 本次计算完成时间 |

#### 明细追溯内容

- 使用的规则编号及规则版本；
- 命中的生效条件；
- 原始输入字段和值；
- 执行的计算公式；
- 中间计算结果；
- 封顶、扣减或调整过程；
- 最终输出结果。
- 正式计算使用的函数本体快照及其与插件版本的关联。

### 6.6 工作流中心

#### 功能说明

工作流中心提供管理员制定的绩效审核流程，供组内成员使用。管理员运行产生正式落库结果；成员运行只产生个人暂存和导出内容。

#### MVP 功能

- 选择标准绩效核算工作流；
- 创建、暂停、恢复和终止计算批次；
- 展示当前节点、执行状态、操作人和异常数量；
- 在数据校验、结果复核节点处理异常后继续执行；
- 支持从失败节点重试，避免重复导入或重复计算；
- 管理员正式计算时冻结规则版本、插件版本、函数本体、输入快照和结果快照。
- 成员运行结果只能进入暂存和导出路径，不得发布为正式绩效。

#### 验收标准

- 操作员可在不编辑规则的情况下完成一次标准核算；
- 工作流可清晰展示当前批次停留的节点及下一步操作；
- 计算失败后可重试失败节点，不影响此前成功节点的结果；
- 已发布的结果可回溯到完整的工作流执行记录。

### 6.7 导出功能

#### MVP 导出内容

- 绩效汇总表；
- 个人绩效明细表；
- 异常数据清单；
- 当前规则表；
- 计算任务记录。

### 6.8 特殊绩效与申诉

#### 已确定范围

- 成员可以针对本人绩效提交申诉。
- 管理员负责审核成员提交的特殊绩效计算或申诉。
- 成员侧通过插件或工作流生成的结果仅可暂存和导出，不能自行写入正式绩效。
- 管理员的正式计算必须落库，并保留实际使用的函数本体和计算上下文。

#### 已确定流程

- 特殊绩效与申诉均为需要材料提交和审批的复杂绩效事项；申诉必须关联本人原正式结果版本。
- 事项依次经历 `draft → submitted → reviewing → approved → processed`；草稿内可修改业务字段和材料，提交后冻结。
- 管理员打回或专用处理插件失败时，事项回到 `draft`，但提交快照、材料版本、意见和失败原因保留。
- 处理人与复核人通过独立接口记录，当前均临时由 `ADMIN` 担任；默认时限为提交后三天，时限修改接口同样临时由 `ADMIN` 调用并记录原因。
- 审核通过后只能调用专用插件，插件生成关联事项的 `approved` 成果来源；管理员再发起正式重算，创建新的结果版本，不直接修改正式结果。
- 通知仅保留服务接口和事件，不实现消息发送。

#### M7 实施状态

特殊绩效与申诉的 API、成员提交页面、管理员审核队列、材料版本和专用插件处理已实现。材料当前保存于 MySQL `MEDIUMBLOB`，单文件上限 10 MiB、每事项最多 20 份当前材料。M7 Alembic 迁移已在获授权的本地开发库执行；其他环境启用此流程前须按各自变更流程备份并迁移。

#### 基础验收场景

1. 成员只能查询和导出自己的绩效，不能修改插件、插件版本或工作流定义。
2. 成员可以使用管理员提供的插件和工作流；运行结果进入个人暂存/导出路径，不改变正式绩效。
3. 成员可以提交本人绩效申诉；草稿可修改材料，提交后不可修改，打回后才可再次编辑。
4. 管理员执行基础绩效计算后，正式计算及结果落库，并能查到输入、规则/插件/工作流版本和实际函数本体。
5. 管理员可以处理和复核特殊绩效计算或申诉；通过事项经专用插件形成可核算成果，重新核算后生成可追溯的新正式结果版本。

## 8. 业务规则

### 8.0 已确定业务规则

- 插件用于帮助管理员快速编写工作流。
- 只有管理员可以修改插件和设置插件版本；成员可以使用管理员提供的插件。
- 管理员制定绩效审核工作流，供组内成员使用；成员不得修改工作流或插件定义。
- 管理员负责工作流和插件的编写与统一，执行基础绩效计算，并审核成员提交的特殊绩效计算或申诉。
- 成员可以查看、导出自己的绩效，并可以提交申诉。
- 成员使用插件或工作流所得结果只能暂存和导出，不产生正式绩效落地或效益。
- 管理员执行的正式计算必须实际持久化。
- 正式计算必须保存当次实际使用的函数本体，而不只是字段、函数名称或版本号。
- 正式结果、计算输入、函数本体及规则/插件/工作流快照应互相关联，以支持历史追溯。
- 特殊绩效与申诉必须提交材料并经审批；材料在草稿内可修订、提交后冻结，打回或插件失败才回到草稿。
- 特殊事项通过后只允许专用插件创建 `approved` 成果来源，再由管理员重新核算生成新的正式结果版本；不得直接修改正式结果。
- 默认审核时限为提交后三天，处理人与复核人使用独立接口但当前均为 `ADMIN`；通知只预留接口和事件。

### 8.0.1 待确定业务规则

以下事项尚无决定，不作为当前实现的既定业务口径：

| 待确定事项 | 需要明确的问题 |
|---|---|
| 管理员层级与组织范围 | 是否区分系统、校级、学院管理员；各自能管理和查看哪些组织的数据？ |
| 成员试算暂存 | 暂存保存哪些输入、输出和函数内容？保留多久？成员能否删除？管理员是否可见？ |
| 插件版本治理 | 谁审核新版本？版本何时生效？是否允许回滚或停用？停用是否影响既有定义？ |
| 函数本体保存方案 | 保存源码、受限中间表示还是可复现制品？依赖如何固定？历史函数是否支持重放？ |
| 数据保留 | 正式计算、申诉材料、日志和成员暂存分别保留多久，哪些角色可以清理？ |
| 导出治理 | 导出格式、字段脱敏、批量导出权限、导出文件有效期和水印要求是什么？ |
| 审计范围 | 是否记录查看、导出、试算、审核和申诉处理等行为？审计日志保留多久？ |

### 8.1 规则匹配

- 仅执行状态为“启用”的规则；
- 规则必须处于当前计算周期的生效日期范围内；
- 人员数据满足生效条件时，规则才可执行；
- 多条规则可同时命中，按优先级执行；
- 同一输出字段的多个结果默认累加；
- 如规则设置“覆盖模式”，高优先级规则可覆盖低优先级结果。

### 8.2 数据校验

- 工号必须唯一；
- 金额、课时数、系数等数值字段必须符合格式；
- 公式中引用的字段必须存在；
- 日期必须符合计算周期；
- 成果、课程等明细数据需关联到具体人员；
- 缺失必要输入时，该条结果标记为异常。

### 8.3 结果冻结

- 每次完成计算后生成一个结果版本；
- 历史结果、规则版本和原始输入不可被后续修改影响；
- 历史正式计算内容保持可追溯；特殊绩效或申诉通过后，经专用插件生成可核算成果并由管理员重新核算创建新版本，不覆盖或撤回原版本；
- 系统需保留历史版本供审计和比对。

| 功能 | 管理员 | 组内成员 |
|---|---:|---:|
| 创建/修改插件及设置插件版本 | 是 | 否 |
| 制定/修改绩效审核工作流 | 是 | 否 |
| 使用插件和工作流 | 是 | 是 |
| 执行基础绩效正式计算并落库 | 是 | 否 |
| 审核特殊绩效计算或申诉 | 是 | 否 |
| 查看个人绩效 | 是（管理范围待定） | 是，仅本人 |
| 导出绩效 | 是（管理范围待定） | 是，仅本人 |
| 提交绩效申诉 | 否（负责受理和处理） | 是 |
| 将特殊事项正式化 | 经专用插件创建可核算成果并重新核算 | 否，仅暂存和导出 |

## 11. 非功能需求

### 11.1 安全性

- 用户需登录后访问系统；
- 组内成员仅可查看本人绩效；
- 管理员的数据访问组织范围为【待确定】；
- 规则修改、数据导入和计算操作需记录日志；
- 导出文件应包含导出人、导出时间和计算版本。
- 成员只能读取和导出本人绩效；成员试算不得进入正式结果。
- 只有管理员可以修改插件、设置插件版本和制定工作流。
- 正式计算应保留执行人、输入、输出、函数本体、规则/插件/工作流快照和执行时间。

### 11.2 性能

MVP 建议目标：

- 支持至少 5,000 名人员；
- 支持至少 100,000 条原始绩效明细；
- 常规批量计算应在 5 分钟内完成；
- 单人结果查询应在 3 秒内返回。

### 11.3 可用性

- 公式错误需提供人类可读的提示；
- 导入失败需定位到具体行和字段；
- 计算异常需区分数据问题与规则问题；
- 所有金额、积分和系数应统一显示精度规则。

## 12. 整体开发路线

计算核心、成果数据、插件、顺序工作流、运行治理和 M7 特殊绩效/申诉闭环已在代码中具备基础实现。当前后续重点为业务验收和运行加固：

1. **P0：函数本体快照。** 正式计算保存当次实际函数实现及校验信息，明确函数来源、依赖和受控执行方式。
2. **P0：管理员正式核算。** 将审核通过的成果按周期和人员范围映射到工作流，建立批次、正式结果和明细版本。
3. **P0：成员自助。** 成员可运行管理员发布的工作流，结果进入与正式绩效隔离的暂存路径；提供本人正式绩效查询、明细和导出。
4. **P1：特殊绩效与申诉（代码已完成，本地开发库迁移已执行）。** 验证申请/申诉、管理员审核、专用插件与正式结果新版本闭环；其他环境迁移需独立授权。
5. **P1：业务验收和运行加固。** 完成端到端验收、备份恢复、监控与容量检查。

具体依赖、工作项和验收门槛以[整体开发文档第 13 节](整体开发文档.md)和[项目管理文档第 4、6 节](项目管理文档.md)为准。成员暂存保留期和管理员组织范围仍需单独确定；M7 已确认流程以[特殊绩效与申诉设计.md](特殊绩效与申诉设计.md)为准。

## 13. MVP 迭代范围

| 顺序 | 交付范围 | 优先级 | 业务验收 |
|---|---|---|---|
| 已完成 | 成果导入/申报与审核、受控函数、计算记录、插件、顺序工作流、跨表链接及运行治理 | 已完成 | 仅已审核成果可供后续计算取数；运行记录可追溯 |
| 下一批 | 实际函数本体快照、管理员正式核算批次和结果版本 | P0 | 管理员结果落库，能还原输入、函数本体及各定义版本 |
| 后续 | 成员工作流暂存、本人绩效查询和导出 | P0 | 成员试算不影响正式绩效；只能查询和导出本人结果 |
| 已开发（本地开发库迁移已执行） | 特殊绩效申请、正式绩效申诉、审核与结果更正 | P1 | 全流程有提交、审核、版本和审计记录 |
| 闭环通过后 | 备份恢复、性能和部署加固 | P1 | 业务场景通过验收，运行保障通过演练 |

人员/学院细粒度授权、财务直连、拖拽画布、并行调度和 Go 内核迁移不属于当前业务闭环的前置范围，后续按使用反馈单独评估。

## 14. 风险与应对

| 风险 | 说明 | 应对方式 |
|---|---|---|
| 规则过于复杂 | 不同学院规则表达差异大 | 先支持高频规则，逐步扩展函数库 |
| 公式配置错误 | 管理员可能误填公式 | 提供校验、试算与规则预览 |
| 原始数据质量差 | 导入字段缺失、格式不统一 | 提供模板、字段映射和错误清单 |
| 历史结果争议 | 规则变动后难以解释旧结果 | 冻结规则、输入和计算明细 |
| 权限边界不清 | 绩效数据具有敏感性 | 采用按角色和学院的数据权限 |

## 15. 数据 MVP：统一成果与审核

教学工作量、论文、项目、经费、社会服务和人才培养等数据先统一为成果记录，至少包含教师、类型、等级、时间、状态和来源原始数据。系统支持教务、科研来源的接口导入与教师手工申报；所有记录先进入院系审核，审核通过后才可作为规则表的 Input 参与绩效计算。当前 `ADMIN` 暂承担院系审核角色，后续按院系范围拆分权限。

## 16. 核心价值

该系统的核心不是“替高校写一套固定绩效规则”，而是提供一个可配置的绩效计算内核。

通过统一的“输入—函数—输出”模型，学校可以把不断变化的绩效政策转化为可维护、可执行、可解释的规则表；管理员能够快速完成核算，教职工能够理解结果来源，管理部门能够保留完整的审计链路。
