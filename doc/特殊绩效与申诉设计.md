# 特殊绩效与申诉设计

## 1. 范围与定义

特殊绩效与申诉用于处理不能直接由常规成果导入或常规规则完成核算、且必须提交证明材料并经人工审批的复杂绩效事项。

- **特殊绩效申请**：成员申报一项待认定的特殊成果或绩效事项。
- **绩效申诉**：成员针对自己的某个正式绩效结果版本提出更正请求。

两类事项共用材料、状态、时限、处理和复核轨迹；申诉必须关联原正式结果版本，特殊绩效申请不关联原结果版本。

## 2. 材料与不可变边界

申请包含业务表单和材料条目。材料内容以 MySQL `MEDIUMBLOB` 保存，每个文件最多 10 MiB，每个事项最多 20 份当前材料。草稿状态下可新增、替换或删除；替换生成新版本，删除只撤下当前版本，文件内容和摘要均保留。

提交时，系统冻结提交快照，包括业务字段、材料清单及材料版本。当前快照保存在事项记录中，每次提交的完整快照也追加写入 `case_submitted` 领域事件，避免后续重提覆盖历史版本。`submitted` 及之后状态不能由成员修改；如被打回，事项回到 `draft`，成员可基于原提交快照继续修改后再次提交。已提交版本、审批意见和插件执行记录始终保留。

## 3. 状态流转

```text
draft → submitted → reviewing → approved → 专用处理插件 → 可核算成果记录
  ↑          │             │                    │
  └──────────┴── 打回 / 插件失败 ────────────────┘
```

| 状态 | 含义 | 可执行人 | 下一步 |
|---|---|---|---|
| `draft` | 可编辑草稿，包含材料修订 | 提交成员 | 提交 |
| `submitted` | 已冻结，等待受理 | 管理员 | 受理或打回 |
| `reviewing` | 管理员处理中 | 处理人（当前为 `ADMIN`） | 通过或打回 |
| `approved` | 复核通过，等待或正在处理专用插件 | 复核人（当前为 `ADMIN`） | 插件成功或失败 |
| `processed` | 插件已产生可核算成果来源 | 系统 | 进入下一次正式核算 |

审核打回或专用插件执行失败均回到 `draft`。失败原因、处理记录和已有提交快照保留；成员不能修改已经冻结的版本，只能在回到草稿后创建下一次提交。

## 4. 处理、复核与时限

处理人与复核人使用独立接口和独立字段记录。当前二者均临时绑定为 `ADMIN`，但模型和审计必须分别保存 `processed_by_user_id` 与 `reviewed_by_user_id`，为后续角色拆分预留边界。

事项提交后的默认处理时限为三天：`review_due_at = submitted_at + 3 天`。管理员可通过独立时限调整接口修改截止时间，调整必须填写原因并写入审计。超过时限不自动通过、打回或修改结果；只形成可查询的逾期状态。

## 5. 审核通过后的正式化与更正

审核通过不允许直接写入 `formal_calculation_results`，也不允许直接覆盖既有正式结果。

1. 系统以已冻结的申请快照调用管理员配置的专用处理插件。
2. 插件仅能通过受控函数契约产出一条可追溯的成果记录；该记录标记为 `approved`，关联申请、提交快照、插件版本和函数本体快照。
3. 该成果记录进入现有 M5 正式核算输入范围。
4. 管理员发起对应人员与周期的重新核算，系统创建新的 `result_version`，历史批次和结果不被覆盖。

对于绩效申诉，专用插件可生成经确认的补正或扣减成果来源；原正式结果版本保持不变，新版本通过上述重新核算产生。处理意见、差异依据、原结果版本和新结果版本必须可以相互追溯。

## 6. 接口边界与通知预留

专用插件使用规则插件的 `purpose=special_case` 标记。它必须是已启用版本，函数引用仍使用现有受控注册函数或外部执行器；插件输入为冻结的事项快照和材料元数据，输出必须符合 `achievement_type`、`level`、`occurred_at`、`payload` 契约。专用插件不能作为普通工作流节点。

成员创建申诉时，服务端从登录账号的 `teacher_id` 取得身份，并校验原结果属于本人且所属批次已复核。特殊绩效申请的教师 ID 同样由账号确定，姓名、院系和周期作为业务表单字段提供。提交时必须至少有一份当前材料；响应含提交版本快照、材料清单、处理/复核人与事件轨迹。

接口如下，均位于 `/api/v1`：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `POST` | `/special-performance-cases` | `USER` | 创建特殊绩效草稿或关联本人正式版本的申诉草稿 |
| `GET` | `/special-performance-cases/mine` | `USER` | 查询本人事项 |
| `GET` | `/special-performance-cases` | `ADMIN` | 查询审核队列，可按状态和逾期过滤 |
| `GET` | `/special-performance-cases/{id}` | 本人 / `ADMIN` | 查询事项、材料元数据和事件历史 |
| `PATCH` | `/special-performance-cases/{id}` | `USER` | 修改本人草稿业务字段 |
| `POST` | `/special-performance-cases/{id}/materials/{key}?filename=...` | `USER` | 上传原始文件内容；同一 key 上传新版本 |
| `DELETE` | `/special-performance-cases/{id}/materials/{material_id}` | `USER` | 从草稿撤下当前材料版本 |
| `GET` | `/special-performance-cases/{id}/materials/{material_id}/content` | 本人 / `ADMIN` | 下载历史材料内容 |
| `POST` | `/special-performance-cases/{id}/submit` | `USER` | 冻结当前表单与材料，创建三天审核截止时间 |
| `POST` | `/special-performance-cases/{id}/handle` | `ADMIN` | 开始处理或打回草稿 |
| `POST` | `/special-performance-cases/{id}/review` | `ADMIN` | 复核通过并选择专用插件，或打回草稿 |
| `POST` | `/special-performance-cases/{id}/process-plugin` | `ADMIN` | 执行/恢复已通过事项的专用插件 |
| `PATCH` | `/special-performance-cases/{id}/deadline` | `ADMIN` | 调整审核截止时间并填写原因 |

处理与复核为独立接口，并分别记录 `processed_by_user_id`、`reviewed_by_user_id`；当前均授权 `ADMIN`。通知只生成 `notification_requested` 领域事件，不发送站内信或外部消息。

通知只保留 `notification_requested` 事件和通知服务接口契约，不在 M7 实现消息发送、站内信、邮件或重试。状态变更、时限调整和插件失败仍必须写入审计，供后续通知服务补发。

## 7. 验收边界

- 成员只能编辑自己的草稿和草稿材料；提交后修改被拒绝。
- 管理员可独立处理和复核；打回或插件失败后事项回到草稿并保留历史。
- 通过事项只能经 `purpose=special_case` 的专用插件创建可核算成果来源，不能直接改写正式绩效。
- 重新核算生成新的正式结果版本；原结果、材料、处理意见、插件快照和审计记录可追溯。
- 默认三天时限可由管理员调整并记录原因；通知服务仅有接口预留。
