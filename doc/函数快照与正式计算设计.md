# 函数快照与正式计算设计

## 1. 目标与边界

M4 为每一次正式计算尝试保存实际使用的函数本体，使历史结果不依赖当前注册表、插件或工作流的状态。`Function` 字段仍是受控 JSON 引用，不能由调用方提交或运行任意源码；函数本体快照由服务端在受控执行前生成。

当前正式计算仍由 `ADMIN` 发起。成员暂存、细粒度角色权限和组织范围控制不属于 M4，本阶段保持挂起。

## 2. 快照策略

### 2.1 已注册 Python 函数

服务端在创建执行尝试时，从受控注册表解析函数，并把以下内容写入 `calculation_attempts.function_body_snapshot`：

- 实际 handler 的模块、限定名和 Python 源码；
- 输入 Pydantic 模型的源码及 JSON Schema；
- 输出 Schema；
- Python 实现、版本及 `pydantic` 版本；
- 对上述内容按稳定 JSON 序列化计算的 `content_sha256`。

这既保存了实际计算公式，也保存了该公式当时的输入契约。执行仍只会调用注册表中的函数；快照只是留存和校验材料，不会被重新执行。

### 2.2 外部执行器函数

外部函数若要进入正式计算，部署配置中的对应执行器必须提供同一 `(name, version)` 的 `function_artifacts` 条目。条目含已审核的 Python 源码、依赖版本和源码 SHA-256。核心校验配置摘要后，将该制品内容与执行器固定路径、超时配置写入尝试快照；记录中不会保存 URL 或令牌。

未配置制品的外部函数在尝试开始前失败，并返回 `FUNCTION_SNAPSHOT_UNAVAILABLE`。这避免把“仅有远程名称和版本”的调用误标为可追溯的正式计算。

## 3. 执行与关联

每条新执行尝试同时保存：

| 字段 | 用途 |
|---|---|
| `function_snapshot` | 原始函数引用，插件记录还保存冻结插件引用及默认输入。 |
| `function_body_snapshot` | 实际函数本体、契约、运行依赖与内容摘要。 |
| `execution_context_snapshot` | 记录 ID、逻辑表、周期、正式计算发起人、插件快照和工作流运行 ID。 |
| `input_snapshot`、`output_snapshot`、`error_snapshot` | 本次实际输入、输出或失败原因。 |

`calculation_records` 增加 `requested_by_user_id` 和 `workflow_run_id`。直接创建记录时保存管理员发起人；工作流中创建的每个底层记录关联该次工作流运行。工作流运行本身已保存工作流键、版本、周期、上下文和请求人，因此可由计算记录回溯到完整工作流上下文。

## 4. 摘要校验与历史兼容

查询 `GET /api/v1/records/{record_id}/attempts` 时，每条尝试返回函数本体快照和 `function_body_snapshot_verified`：

- `true`：快照的 `content_sha256` 与保存内容匹配；
- `false`：保存内容已损坏或被篡改，应停止将该尝试作为可验证依据；
- `null`：M4 前创建的历史尝试，只保留函数引用，属于 `legacy_reference_only` 兼容语义。

快照是 append-only 的执行历史。修改、停用或新增当前函数／插件版本不会回写历史尝试；重试会创建一条新的尝试和新的当次快照。

## 5. 数据迁移与运维

Alembic 迁移 `20261018_0007` 新增函数本体快照、执行上下文、请求人和工作流运行关联字段。所有新增列对已有数据允许为空，避免将旧记录伪造为包含函数本体的记录。

正式部署应把外部函数制品配置与执行器代码发布绑定，并在发布前校验其 SHA-256。函数快照可能包含业务公式，应按正式计算数据的访问、备份和审计要求保护，不能向非授权用户暴露。
