# NumCounts 项目管理文档

## 1. 项目管理目标

项目管理的目标是在不牺牲计算语义和数据可追溯性的前提下，逐步将最小原型发展为可在高校绩效场景中运行的系统。每个阶段以可验证的能力交付为边界，而不是以代码数量或页面数量作为完成标准。

项目的首要约束是：规则变化可配置、结果可解释、失败可定位、重试不影响无关记录。任何需求、技术方案和发布决策都不得突破这些约束。

## 2. 角色与职责

| 角色 | 主要职责 | 关键交付物 |
|---|---|---|
| 产品负责人 | 确认场景、规则优先级、验收结果和范围取舍 | 产品需求、验收用例、发布决策 |
| 技术负责人 | 架构、数据模型、接口边界、技术风险和代码质量 | 技术方案、设计评审、发布批准 |
| 后端开发 | FastAPI、计算核心、MySQL、执行器和接口实现 | 可测试的服务与迁移脚本 |
| 前端开发 | 管理端、记录查询、规则配置、结果与错误展示 | 可用操作界面 |
| 测试负责人 | 测试策略、接口测试、回归与验收组织 | 测试报告、缺陷清单、上线建议 |
| 绩效业务专家 | 提供规则样本、确认计算口径、验证结果 | 规则模板、样例数据、业务验收 |
| 运维或平台负责人 | 环境、发布、监控、备份和安全配置 | 部署方案、运行手册、告警规则 |

同一人可承担多个角色，但产品验收和技术发布至少应由不同角色复核。

## 3. 工作范围管理

### 3.1 MVP 范围

| 能力 | 优先级 | 验收结果 |
|---|---|---|
| 记录的 Input Function Output 模型 | P0 | 创建后可完整查询与追溯 |
| 已登记函数调用与版本校验 | P0 | 未登记函数不能执行 |
| 单线程执行与状态转换 | P0 | 待执行记录有确定执行顺序 |
| 局部重载和重试 | P0 | 失败记录重试不影响成功记录 |
| 两表三规则样例 | P0 | 两条成功，一条失败后仍能明确提示错误 |
| FastAPI 与 MySQL 服务化 | P0 | 同一验收场景可通过 API 完成 |
| 函数目录与输入说明 | P1 | 管理员可查看可调用函数 |
| CSV 或 Excel 导入导出 | P1 | 错误行可定位，结果可导出 |
| 外部执行器 | P1 | 受控 HTTP 调用、超时和错误处理正确 |
| 规则插件与顺序工作流 | 已完成 | 插件版本冻结、节点编排、汇总与运行追溯 |
| 工作流管理界面 | P2 | 可视化操作生成底层记录 |
| 跨表依赖与依赖图 | P2 | 可检测循环并追溯依赖 |
| 多级审批与财务对接 | P3 | 在核心稳定后单独立项 |

P0 是首次可用版本的发布门槛。P1 在 P0 验收通过后排期。P2 和 P3 不得阻塞 P0 服务化。

### 3.2 需求状态

`待澄清 → 待评审 → 已排期 → 开发中 → 测试中 → 待验收 → 已完成`

需求进入“已排期”前必须具备业务目标、范围、接口或界面影响、验收标准、数据影响和负责人。需求发生规则或数据库结构变化时，必须同步更新 [产品需求文档.md](产品需求文档.md) 与 [开发技术文档.md](开发技术文档.md)。

## 4. 里程碑与交付门槛

| 里程碑 | 目标 | 主要交付物 | 通过门槛 |
|---|---|---|---|
| M0 原型基线（已完成） | 固化最小计算语义 | SQLite 原型、两表三规则测试 | 原型回归测试通过 |
| M1 服务基础（已完成） | FastAPI 与本地 MySQL 可运行 | 项目骨架、Alembic、核心表、登录与 JWT、健康检查 | MySQL 迁移与用户种子可重复执行 |
| M2 核心 API（已完成） | 外部系统可使用数据与记录服务 | 成果数据 MVP、创建、查询、执行、重载、重试、尝试历史 API | 成果审核流与计算记录 API 端到端验收通过 |
| M3 规则插件与工作流（已完成） | 操作员编排可追溯核算 | 插件版本、启停、顺序节点、运行历史与汇总 | 插件和工作流运行均可追溯到底层计算记录 |
| M4 操作员闭环 | 管理员完成一次核算 | 导入、批次、错误处理、结果导出 | 业务专家验收计算结果 |
| M5 扩展运行 | 支持复杂规则与稳定运行 | 细粒度权限、监控、备份与恢复 | 压测、恢复和安全检查通过 |

里程碑不以自然日期强行完成。只有通过对应门槛，才能进入下一里程碑的主线开发。

## 5. 迭代节奏

建议采用两周一个迭代。每次迭代只承诺已满足“准备就绪定义”的工作项，保留容量处理缺陷、技术债和业务规则澄清。

| 节点 | 活动 | 输出 |
|---|---|---|
| 迭代计划 | 确认目标、范围、风险和验收样例 | 迭代任务清单 |
| 需求澄清 | 业务专家确认规则输入、公式、边界与结果 | 规则样例与验收数据 |
| 设计评审 | 评审 API、数据迁移、权限与失败处理 | 设计结论与待办 |
| 开发 | 小粒度提交、单元测试、文档同步 | 可评审代码 |
| 联调与测试 | API、数据库迁移、回归和端到端验证 | 测试结果与缺陷 |
| 业务验收 | 使用固定样例验证金额和明细 | 验收结论 |
| 发布回顾 | 发布、监控观察、复盘和待改进项 | 发布记录与行动项 |

### 6.3 M3 及以后任务

M3 已完成插件与顺序工作流的后端交付。M4 优先将已审核成果映射为工作流上下文、导入导出和操作员界面；M5 再引入跨表链接、细粒度权限、监控与恢复。外部执行器基础能力已在阶段二交付。每个工作项均需在项目看板中关联需求、设计、代码、测试和发布记录。

## 7. 准备就绪与完成定义

### 7.1 准备就绪定义

工作项进入开发前必须满足：

- 有清晰业务目标和优先级；
- 有输入、输出、异常和权限边界；
- 有可复现的验收样例；
- 涉及 API 时已有请求、响应与错误码定义；
- 涉及数据库时已有迁移与回滚方案；
- 已识别外部依赖、数据迁移和安全影响。

### 7.2 完成定义

工作项仅在以下条件全部满足时标记完成：

- 代码通过评审并合并到主干；
- 单元测试、接口测试和相关回归测试通过；
- 数据库迁移在空库和升级场景验证通过；
- API 或产品文档已更新；
- 日志、错误处理和权限符合设计；
- 验收标准由产品负责人或业务专家确认；
- 发布说明、监控项和回滚步骤已准备。

## 8. 质量管理

| 质量维度 | 控制措施 | 门槛 |
|---|---|---|
| 计算正确性 | 固定样例、边界值、回归测试 | 金额、状态、错误和尝试次数全部符合预期 |
| 数据一致性 | 事务、行锁、乐观锁、迁移测试 | 同一记录不出现并行成功提交 |
| 安全性 | Function 白名单、JWT、范围权限、密钥管理 | 不执行任意代码，不泄露敏感信息 |
| 可追溯性 | 输入、函数版本、尝试快照、审计日志 | 任一输出可定位到来源 |
| 可运维性 | 健康检查、结构化日志、指标与备份 | 故障可发现、可定位、可恢复 |
| 文档一致性 | PR 检查清单与设计评审 | 接口、数据模型和实际实现无冲突 |

每个缺陷修复必须包含复现测试。涉及结果金额的缺陷需要业务专家确认修复后的样例结果。

## 9. 分支、代码评审与发布

### 9.1 分支策略

- `main`：始终可部署，受保护，禁止直接提交；
- `feature/<topic>`：一个需求或技术工作项一个分支；
- `fix/<topic>`：缺陷修复分支；
- `release/<version>`：仅在需要稳定发布候选时创建；
- `hotfix/<topic>`：生产紧急修复，合并后同步回 `main`。

提交应小而可理解，消息说明变更目的。涉及 Schema 时，代码、Alembic 迁移和迁移测试必须在同一合并请求中出现。

### 9.2 合并请求检查清单

- 需求与验收标准链接完整；
- 代码、测试和文档一致；
- 不包含密钥、真实绩效数据或生产导出文件；
- 新函数有输入、输出、错误和版本说明；
- 数据库变更有迁移、索引影响和回滚说明；
- API 变更已同步 [API接口文档.md](API接口文档.md)；
- 至少一名技术评审者通过；涉及业务规则时需业务专家复核。

### 9.3 发布流程

1. 主干测试、镜像构建、依赖与安全扫描通过。
2. 在预发布环境执行 Alembic 迁移并运行 API 和业务样例回归。
3. 产品负责人确认发布范围，运维负责人确认备份、监控和回滚条件。
4. 先发布 API，再发布单线程执行器；观察健康检查、错误率和执行积压。
5. 发布后用两表三规则样例完成冒烟验证。
6. 在发布记录中归档版本、迁移、变更、监控观察和回滚结论。

## 10. 风险与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 规则表达超出函数能力 | 频繁请求在字段内写脚本 | 优先新增受控函数或插件契约，不开放任意代码执行 |
| 规则变更破坏历史结果 | 修改现有函数版本或覆盖规则 | 冻结函数版本、输入快照和尝试记录 |
| 并发导致重复执行 | 同一记录出现多次成功尝试 | 保持单执行器，使用行锁和唯一执行 ID |
| 数据导入质量差 | 缺字段、格式异常和人员无法匹配 | 模板、字段映射、预校验和错误行下载 |
| 外部执行器不稳定 | 超时、认证失败或错误响应增加 | allowlist、超时、契约测试、显式重试和监控 |
| 上线迁移风险 | 大表迁移或索引变更耗时异常 | 预发布演练、备份、分步迁移和回滚方案 |
| 敏感绩效数据泄露 | 越权查询或日志包含明细 | 最小权限、审计、脱敏日志和数据保留策略 |

## 11. 项目度量与例会

每周项目例会关注以下指标，而不是仅汇报任务数量：

| 指标 | 目的 |
|---|---|
| P0 工作项完成率与阻塞时长 | 判断 MVP 是否按关键路径推进 |
| 两表三规则验收通过率 | 监控核心计算语义是否回归 |
| API 自动化测试通过率 | 监控服务接口质量 |
| 生产或预发布失败记录占比 | 发现规则、输入或执行器问题 |
| 最长 `pending` 等待时间 | 发现执行积压 |
| 缺陷重开率与逃逸缺陷数 | 评估测试与评审有效性 |
| 文档更新滞后项 | 防止设计与实现分离 |

阻塞超过一个迭代或影响 P0 的事项必须形成明确决策：调整范围、补充资源、拆分交付或延后非关键能力。所有架构取舍和规则口径变化应记录在决策日志中。
