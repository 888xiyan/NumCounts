# NumCounts 规则插件与工作流设计

## 1. 目标与边界

本阶段把计算内核包装成管理员和组内成员可使用的两层能力：规则插件负责把受控函数和常用默认参数封装成可复用规则；工作流负责按固定顺序传入参数、触发计算并汇总结果。管理员负责插件和工作流的编写与统一；成员可使用它们，但成员侧运行只能暂存和导出，不得形成正式绩效结果。管理员执行的正式计算必须持久化。

只有管理员可以修改插件和设置插件版本；成员没有插件或工作流定义的编辑权限。正式计算记录必须保存当次实际执行的函数本体快照，以支持历史追溯。函数快照如何序列化、保存在数据库还是不可变制品存储、如何固定运行依赖，仍为待确定的技术方案。无论快照采用何种形式，函数只能通过受控登记和执行器运行，不能执行任意 Python、JavaScript、SQL、Shell 或 URL。

成员运行需与正式运行区分持久化语义：正式计算保存完整计算记录、输出和函数快照；成员运行仅限个人暂存和导出，不写入正式绩效结果。暂存数据保存期限、管理员可见性、成员删除权和物理存储方式待业务确认。

本阶段实现顺序工作流，支持两种节点：

- `plugin`：从工作流上下文和固定字面量构造输入，使用冻结的插件版本创建并执行一条计算记录。
- `aggregate`：读取前序成功节点的 `output.amount`，调用内置 `aggregate_amounts@1.0.0` 创建并执行一条汇总计算记录。

不实现任意表达式、分支、并行、循环、跨表动态查询、自动重试和拖拽画布编辑器。`frontend/` 已提供无需构建工具的本地操作台，用于登录、配置插件和工作流、启停及查看运行结果；它只调用本阶段 API，不能绕过内核写结果。

## 2. 规则插件

### 2.1 插件模型

一条插件记录是不可修改的版本化函数快捷方式。只有管理员可以创建或修改插件及设置版本。创建后默认为 `disabled`；只有启用的插件可被新规则记录或新工作流定义引用。需要修改参数或函数时，创建相同 `plugin_key` 的新 `version`，不覆盖历史版本。启停策略作为当前实现规则；其业务审批、生效和回滚要求仍待确定。

```json
{
  "plugin_key": "teaching_hourly",
  "version": "1.0.0",
  "name": "教学课时绩效",
  "description": "按核定课时和固定单价计算教学绩效",
  "function": {
    "kind": "registered",
    "name": "teaching_performance",
    "version": "1.0.0"
  },
  "input_defaults": {
    "rate": 80,
    "quality_factor": 1.1
  }
}
```

`function` 只能引用已登记的 `registered` 函数或已受控配置的 `external` 执行器，不能再引用另一个插件。`input_defaults` 与调用方提交的 `input` 合并，调用方同名字段优先。

创建使用插件的正式计算记录时，核心至少保存插件 ID、键、版本、显示名称、函数引用、默认输入和实际执行的函数本体快照。执行时使用已冻结的快照语义，而不是重新读取插件当前状态。因此，停用插件不会改变历史计算语义。函数本体快照的序列化与存储形态待技术方案确定；当前仅保存 `function` 引用的实现需要补足此要求。

### 2.2 插件操作

| 操作 | 接口 | 权限 | 结果 |
|---|---|---|---|
| 创建版本 | `POST /api/v1/rule-plugins` | `ADMIN` | 创建 `disabled` 插件版本 |
| 查询目录 | `GET /api/v1/rule-plugins` | `ADMIN` | 返回版本、函数、默认输入和状态 |
| 查看版本 | `GET /api/v1/rule-plugins/{id}` | `ADMIN` | 返回完整插件元数据 |
| 启用 | `POST /api/v1/rule-plugins/{id}/enable` | `ADMIN` | 允许新引用 |
| 停用 | `POST /api/v1/rule-plugins/{id}/disable` | `ADMIN` | 拒绝新引用，保留历史执行 |

通过插件创建普通计算记录时，`Function` 字段使用引用而非源码：

```json
{
  "kind": "plugin",
  "plugin_id": "11111111-1111-1111-1111-111111111111"
}
```

记录响应的 `plugin` 字段返回冻结快照，执行尝试中的 `function_snapshot` 同时保留插件引用和最终解析出的受控函数，保证结果可解释。

## 3. 工作流

### 3.1 定义与版本

工作流由 `workflow_key + version` 稳定标识。管理员制定和维护工作流。定义创建后为 `draft`，只能整体启用或停用，不能原地编辑节点；改变节点、插件或参数时应创建新版本。`active` 工作流可供管理员和组内成员使用；管理员运行按正式计算语义落库，成员运行只进入暂存/导出路径。`disabled` 和 `draft` 工作流拒绝新运行。

工作流节点按 `position` 顺序执行。聚合节点只能引用之前已经定义的节点，创建请求会拒绝倒序引用和重复节点键，从而不需要运行时猜测依赖关系。

```json
{
  "workflow_key": "annual_performance",
  "version": "1.0.0",
  "name": "年度教学科研绩效",
  "nodes": [
    {
      "node_key": "teaching",
      "node_type": "plugin",
      "config": {
        "plugin_id": "11111111-1111-1111-1111-111111111111",
        "table_name": "teaching_results",
        "input_bindings": {
          "hours": {"kind": "context", "key": "approved_hours"}
        }
      }
    },
    {
      "node_key": "total",
      "node_type": "aggregate",
      "config": {
        "table_name": "performance_summary",
        "source_node_keys": ["teaching"]
      }
    }
  ]
}
```

插件节点在创建工作流定义时冻结插件快照。`input_bindings` 只支持两种显式值来源：

| 绑定 | 示例 | 语义 |
|---|---|---|
| 上下文 | `{"kind":"context","key":"approved_hours"}` | 读取运行请求 `context.approved_hours` |
| 字面量 | `{"kind":"literal","value":80}` | 写入固定 JSON 值 |

没有表达式语言、变量插值或远程数据读取；缺少必需上下文时节点失败，错误码为 `WORKFLOW_CONTEXT_VALUE_MISSING`。

### 3.2 运行语义

`POST /api/v1/workflows/{id}/runs` 创建一次运行，并在 MVP 中同步顺序执行。每个节点都会得到一条 `workflow_run_nodes` 记录和其关联的 `calculation_record_id`。

```text
创建运行 running
  ├── 插件节点 → 创建 calculation_record → 执行 → success / failed
  ├── 汇总节点 → 读取前序 output.amount → 创建 calculation_record → 执行
  └── 全部成功 → workflow_run success

任一节点失败
  ├── 当前节点 failed，保留计算记录与错误快照
  ├── 后续节点 skipped，原因 UPSTREAM_NODE_FAILED
  └── workflow_run failed
```

运行成功后，`workflow_runs.result_data` 使用节点键保存各节点输出；运行节点仍是详情和追溯的主入口。单条计算记录可继续使用已有的局部重载和重试接口；需要重新执行整套流程时，以相同上下文发起新的工作流运行，旧运行始终保留。

### 3.3 工作流接口

| 操作 | 接口 | 权限 |
|---|---|---|
| 创建草稿 | `POST /api/v1/workflows` | `ADMIN` |
| 查询定义 | `GET /api/v1/workflows`、`GET /api/v1/workflows/{id}` | `ADMIN` |
| 启用或停用 | `POST /api/v1/workflows/{id}/activate`、`POST /api/v1/workflows/{id}/disable` | `ADMIN` |
| 发起正式运行 | `POST /api/v1/workflows/{id}/runs` | `ADMIN`；必须保存计算记录、结果及实际函数本体 |
| 发起成员运行 | 工作流运行接口（具体成员 API/数据模型待定） | 组内成员；仅本人暂存和导出，不产生正式绩效 |
| 查询正式运行 | `GET /api/v1/workflows/{id}/runs`、`GET /api/v1/workflow-runs/{run_id}` | `ADMIN`；成员运行查询范围待实现方案明确，业务上仅允许本人访问 |

运行请求示例：

```json
{
  "period_id": "2026-annual",
  "context": {
    "approved_hours": 36
  }
}
```

## 4. 数据表与追溯

| 表 | 用途 |
|---|---|
| `rule_plugins` | 插件稳定键、版本、函数引用、默认输入和启停状态 |
| `workflow_definitions` | 工作流稳定键、版本、显示信息和状态 |
| `workflow_nodes` | 顺序节点、配置和冻结插件快照 |
| `workflow_runs` | 一次操作员运行的周期、上下文、状态、汇总结果和错误 |
| `workflow_run_nodes` | 节点执行状态、输入/输出/错误快照以及计算记录关联 |
| `calculation_records` | 正式计算的事实来源；应保存 `plugin_id`、插件快照及当次实际函数本体快照。快照字段和制品存储形态待定 |
| 成员暂存运行 | 非正式个人运行的暂存/导出数据；表结构、保留期限与管理员可见性待业务及技术方案确定 |

Alembic 迁移 `20261018_0005` 一次性创建上述工作流和插件表，并扩展计算记录。升级后执行 `alembic upgrade head` 即可。

## 5. 验收场景

1. 管理员创建 `teaching_hourly@1.0.0` 插件，引用 `teaching_performance@1.0.0` 并设置 `rate=80`、`quality_factor=1.1`，启用该插件。
2. 管理员创建包含 `teaching` 插件节点和 `total` 聚合节点的年度工作流，启用该工作流。
3. 以 `approved_hours=36` 发起运行。`teaching` 节点输出 `3168.0`，`total` 节点输出 `3168.0`；两条底层计算记录和两条节点运行记录均为成功。
4. 缺少 `approved_hours` 时，`teaching` 失败并返回 `WORKFLOW_CONTEXT_VALUE_MISSING`，`total` 标记为 `skipped`，整次工作流为 `failed`。
5. 停用插件后，新普通计算记录和新工作流定义不能引用该插件；已创建的工作流版本仍使用冻结快照，历史运行和记录不被改变。
