# 管理员正式核算设计

## 1. 目标与范围

M5 将已审核成果、绩效周期、已启用工作流和正式计算结果连接为管理员可复核的核算批次。每次重新核算都会为每位教师创建新的结果版本，历史批次、结果、成果来源、工作流运行和函数本体快照均不被覆盖。

本阶段只提供 `ADMIN` 发起、查询和确认复核的接口。成员试算、成员可见范围、个人导出与申诉属于 M6 及以后阶段。

## 2. 批次输入契约

创建批次必须指定：

- `period_id`、`occurred_from`、`occurred_to`；
- 已启用工作流和作为最终金额来源的 `result_node_key`；
- 可选院系与教师 ID 范围；为空时使用周期内所有匹配的已审核成果；
- 一组成果输入映射。

成果输入映射是声明式的固定聚合，而不是公式语言：每项只允许按成果类型、等级筛选后进行 `count` 或对一个 `payload_key` 做 `sum`。映射输出成为该教师工作流的上下文值。缺失或非数值的求和字段会使对应教师结果失败并保留错误，不会把未经验证的数据传入函数。

## 3. 数据与追溯关系

| 实体 | 主要内容 |
|---|---|
| `formal_calculation_batches` | 周期、范围、工作流完整快照、输入映射快照、发起人、复核状态和批次错误。 |
| `formal_calculation_results` | 每位教师在该批次的一项结果、周期内递增的 `result_version`、工作流运行、金额、完整节点输出或错误。 |
| `formal_calculation_result_sources` | 结果所使用的每条成果 ID 及创建批次时的成果快照。 |

每个结果还经由 `workflow_run_id` 关联到底层计算记录；计算记录的尝试历史保存函数本体、内容摘要、输入、输出和执行上下文。因此可以从正式金额反查到成果来源、工作流/插件版本和实际函数内容。

## 4. 运行与状态

批次按教师逐一同步运行工作流：

1. 仅读取 `approved` 且位于周期、人员、院系范围内的成果。
2. 按教师汇总固定映射，调用冻结的已启用工作流。
3. 保存每位教师的新正式结果和全部成果来源快照。
4. 全部成功时批次进入 `pending_review`；任一教师失败时批次进入 `failed`，成功和失败结果都可查询。
5. 管理员调用确认接口后，成功批次变为 `reviewed`，并写入审计事件。

复核确认不会修改结果金额。需要重新核算时创建新的批次，目标教师的 `result_version` 递增，旧版本继续保留。撤回、发布、二次审批和组织范围规则仍待业务确认。

## 5. API

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/formal-calculation-batches` | 创建并同步执行一个正式核算批次 |
| `GET` | `/formal-calculation-batches` | 按周期或状态查询批次 |
| `GET` | `/formal-calculation-batches/{id}` | 查询批次、结果和成果明细 |
| `POST` | `/formal-calculation-batches/{id}/review` | 确认待复核的成功批次 |
| `GET` | `/formal-calculation-results` | 按批次、周期或教师查询版本化结果 |
| `GET` | `/formal-calculation-results/export` | 导出指定批次或周期内成功结果及成果来源明细 |

接口详细参数与响应见 [API接口文档.md](API接口文档.md)。

## 6. 迁移与限制

Alembic 迁移 `20261020_0008` 创建批次、结果和成果来源表；`20261020_0009` 将结果金额列与 ORM 的 `DOUBLE` 类型对齐。它们不修改历史计算记录或成果数据。

单批次最多读取 10,000 条成果；超出该规模的并发调度和批量分片属于后续性能工作。管理员组织范围未在本阶段实现，因此当前 `ADMIN` 可按请求范围发起核算；M6 前不得将这些正式结果暴露给普通成员。
