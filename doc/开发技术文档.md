# NumCounts 开发技术文档

## 1. 项目背景

高校绩效规则覆盖教学、科研、管理、奖励和扣减等多个维度，并随学校、学院、岗位和考核周期变化。传统电子表格将输入、公式和结果分散保存，容易出现规则误改、版本混用、结果难追溯和人工汇总成本高的问题。

NumCounts 以表记录为核心。每条记录均包含 `Input`、`Function` 和 `Output`：输入保存业务数据，函数描述受控计算逻辑，输出保存计算结果。计算核心负责校验、调度、执行、状态转换和结果追溯；插件用于封装复杂业务函数；工作流用于帮助操作员完成导入、计算、复核和导出。

本技术方案以 FastAPI 和 MySQL 为正式系统技术栈。Python 与 SQLite 原型仍用于验证最小语义；M0、M1、M2、M3 已迁移为可运行的正式服务，后续功能必须保持 Input、Function、Output 和局部重试语义不变。

## 2. 建设目标与范围

### 2.1 MVP 目标

- 通过 API 创建、查询和执行绩效计算记录；
- 支持已登记函数的安全调用，不执行记录字段中的任意代码；
- 保存输入、函数版本、输出、失败原因和执行历史；
- 支持单条记录局部重载和重试；
- 支持两张逻辑表中的多条规则独立执行，单条失败不影响其他记录；
- 为插件、工作流、跨表链接、权限和审计保留稳定扩展点。

### 2.2 MVP 非目标

- 不支持插队、自动重试、批量重载和跨表依赖调度；
- 不支持自由编写 Python、JavaScript 或 SQL 公式；
- 不直接对接工资发放、教务、科研和人事系统；
- 不提供完整的工作流画布和多级审批；
- 不以高并发任务调度为首要目标。

## 3. 技术栈

| 层级 | 技术 | 用途 |
|---|---|---|
| 后端语言 | Python 3.12 | 服务实现与业务函数开发 |
| Web 框架 | FastAPI | REST API、请求校验、OpenAPI 文档 |
| 数据校验 | Pydantic v2 | API 请求、函数参数和响应模型 |
| ORM | SQLAlchemy 2.x | MySQL 实体映射、事务与查询 |
| 数据库 | MySQL 8.0 InnoDB | 正式记录、审计与版本数据持久化 |

| 缓存与锁 | Redis 7 可选 | 后续限流、分布式锁和任务通知 |

## 5. 计算核心详细设计

### 5.1 记录模型

```json
{
  "id": "4a353e8e-3578-4dda-954d-5d5063d4509e",
  "table_name": "teaching_rules",
  "period_id": "2026-spring",
  "input": {"hours": 36, "rate": 80, "quality_factor": 1.1},
  "function": {
    "kind": "registered",
    "name": "teaching_performance",
    "version": "1.0.0"
  },
  "output": null,
  "status": "pending",
  "error": null,
  "attempt_count": 0,
  "version": 1
}
```

| 字段 | 含义 | 写入规则 |
|---|---|---|
| `input` | 业务输入 JSON | 创建或修订记录时写入 |
| `function` | 函数类型、名称和版本 JSON | 创建或修订记录时写入 |
| `output` | 成功计算结果 JSON | 仅核心提交 |
| `status` | `pending`、`running`、`success`、`failed` | 仅核心转换 |
| `error` | 标准错误对象或空值 | 仅核心提交 |
| `attempt_count` | 实际执行尝试数 | 每次开始执行时加一 |
| `version` | 乐观锁版本 | 每次更新时加一 |

### 5.2 Function 设计

函数内容必须是 JSON 描述对象，不能保存可执行源码。

```json
{
  "kind": "registered",
  "name": "teaching_performance",
  "version": "1.0.0"
}
```

当前实现支持 `registered` 与 `external`。核心根据 `(name, version)` 在函数注册表中查找内置函数并验证其输入契约；外部函数只允许引用已配置的执行器标识。

复杂业务函数使用外部执行器：

```json
{
  "kind": "external",
  "executor_id": "research-policy-runner",
  "name": "calculate_paper_performance",
  "version": "2.1.0"
}
```

`executor_id` 是受控配置标识。当前执行器元数据、实际 URL、令牌和超时从环境变量读取；后续可迁移到受控配置与密钥管理服务，绝不由记录输入提供。

### 5.3 状态机与事务

```text
创建记录                  → pending
执行：pending/success/failed → running → success 或 failed
局部重载：success/failed/pending → pending
重试：success/failed/pending → pending → running → success 或 failed
```

执行流程：

1. 执行器按创建时间选择一条 `pending` 记录。
2. 在短事务中使用 `SELECT ... FOR UPDATE` 锁定记录，确认状态仍为 `pending`。
3. 将状态设为 `running`，增加 `attempt_count`，创建一条执行尝试记录并提交事务。
4. 事务外调用内置函数或外部执行器，避免长时间占用数据库锁。
5. 在新事务中再次锁定记录，写入 `output` 或 `error`，更新状态并完成执行尝试记录。
6. 事务提交后再处理下一条记录。

局部重载只更新一个记录：清空 `output` 和 `error`，状态回到 `pending`，不修改其他表和其他记录。重试就是局部重载后再次执行。`running` 记录拒绝执行、重载和重试请求。

### 5.4 内置函数输入契约

| 函数 | 输入 | 校验 | 输出 |
|---|---|---|---|
| `teaching_performance@1.0.0` | `hours`、`rate`、可选 `quality_factor` | 数值、非负 | `amount = hours × rate × quality_factor` |
| `course_bonus@1.0.0` | `course_count`、`level` | 数量非负；等级为 `national`、`provincial`、`school` | 对应固定奖励金额 |
| `research_performance@1.0.0` | `papers`、`projects`、`funding` 与可选权重 | 数值、非负 | 论文、项目和经费分项汇总 |

每个函数必须有 Pydantic 输入模型、输出模型、版本、业务错误码和单元测试。函数异常不得穿透到 HTTP 层，而应转换为结构化错误并写入记录。

### 5.5 标准错误对象

```json
{
  "code": "INVALID_FUNCTION_INPUT",
  "message": "function input did not satisfy its contract",
  "retryable": false,
  "details": {
    "errors": ["Pydantic 字段错误明细"]
  }
}
```

| 错误码 | 含义 | 是否可重试 |
|---|---|---|
| `INVALID_RECORD` | 记录结构或输入格式错误 | 否 |
| `FUNCTION_NOT_FOUND` | 函数或版本未登记 | 否 |
| `INVALID_FUNCTION_INPUT` | 内置函数业务输入不合法 | 否 |
| `CALCULATION_ALREADY_RUNNING` | 记录正在执行 | 是 |
| `EXECUTOR_TIMEOUT` | 外部执行器超时 | 是 |
| `EXECUTOR_INVALID_RESPONSE` | 外部执行器响应不符合契约 | 视问题而定 |
| `INTERNAL_ERROR` | 未预期服务异常 | 是 |

## 6. API 设计

所有接口使用 JSON，路径前缀为 `/api/v1`。除健康检查外，接口需要身份认证；MVP 可先使用 JWT，后续接入学校统一身份认证。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/records` | 创建计算记录 |
| `GET` | `/records/{record_id}` | 查询单条记录和最新结果 |
| `GET` | `/records` | 按逻辑表、状态、周期分页查询 |
| `POST` | `/records/{record_id}/execute` | 同步触发指定记录执行 |
| `POST` | `/records/run-pending` | 触发单线程处理待执行记录 |
| `POST` | `/records/{record_id}/reload` | 局部重载记录 |
| `POST` | `/records/{record_id}/retry` | 局部重载后重试 |
| `GET` | `/records/{record_id}/attempts` | 查询执行尝试历史 |
| `GET` | `/functions` | 查询可调用函数与输入说明 |
| `GET` | `/health/live` | 进程存活检查 |
| `GET` | `/health/ready` | 数据库与依赖就绪检查 |

### 6.1 创建记录

```http
POST /api/v1/records
Content-Type: application/json
Idempotency-Key: 4a353e8e-3578-4dda-954d-5d5063d4509e
```

```json
{
  "table_name": "teaching_rules",
  "period_id": "2026-spring",
  "input": {
    "hours": 36,
    "rate": 80,
    "quality_factor": 1.1
  },
  "function": {
    "kind": "registered",
    "name": "teaching_performance",
    "version": "1.0.0"
  }
}
```

响应为 `201 Created` 并返回 `pending` 记录。同一幂等键与相同请求体返回同一记录和 `200 OK`；同一键配合不同请求体返回 `409 IDEMPOTENCY_KEY_REUSED`。

### 6.2 查询与执行响应

```json
{
  "id": "4a353e8e-3578-4dda-954d-5d5063d4509e",
  "table_name": "teaching_rules",
  "status": "success",
  "output": {
    "metric": "teaching_performance",
    "amount": 3456.0
  },
  "error": null,
  "attempt_count": 1,
  "version": 2
}
```

失败时返回 `status=failed` 与标准 `error` 对象。API 层使用 `400` 表示请求格式错误，`401` 表示未认证，`403` 表示无访问权限，`404` 表示记录不存在，`409` 表示状态冲突，`422` 表示输入或函数契约不合法。

### 6.3 外部执行器接口

外部执行器采用受控同步 HTTP 契约：

```http
POST {executor-base-url}/v1/executions
X-Execution-Id: exec_01J...
X-Trace-Id: trace_01J...
Authorization: Bearer <服务端凭证>
```

```json
{
  "execution_id": "exec_01J...",
  "record_id": "4a353e8e-3578-4dda-954d-5d5063d4509e",
  "function": {
    "name": "calculate_paper_performance",
    "version": "2.1.0"
  },
  "input": {
    "paper_level": "A",
    "author_rank": 1,
    "author_count": 3
  },
  "timeout_ms": 5000
}
```

外部执行器只可返回成功输出或标准错误。相同 `execution_id` 必须幂等。核心负责将网络异常、认证失败和无效响应转换为记录错误；外部执行器不能访问 MySQL 或直接改变记录状态。

## 7. 数据库设计

### 7.1 MySQL 设计原则

- 使用 MySQL 8.0、InnoDB、`utf8mb4` 和 UTC 时间；
- 主键使用 `CHAR(36)` UUID，简化外部接口与审计关联；规模增长后可迁移为 `BINARY(16)`；
- 业务可变字段使用 MySQL JSON，状态、索引字段和关联字段使用标准列；
- 使用外键维护强关联，使用逻辑删除或状态归档保护审计数据；
- 所有 Schema 变更必须通过 Alembic 迁移，不允许手工改生产表。

### 7.2 核心表

#### calculation_records

| 字段 | 类型 | 约束与说明 |
|---|---|---|
| `id` | `CHAR(36)` | 主键 UUID |
| `table_name` | `VARCHAR(64)` | 逻辑表名，索引 |
| `period_id` | `VARCHAR(64)` | 考核周期，可为空，索引 |
| `idempotency_key` | `VARCHAR(36)` | 创建请求幂等键，可为空且唯一 |
| `input_data` | `JSON` | Input |
| `function_spec` | `JSON` | Function |
| `output_data` | `JSON` | Output，可为空 |
| `status` | `VARCHAR(16)` | `pending/running/success/failed`，索引 |
| `error_code` | `VARCHAR(64)` | 最近错误码，可为空 |
| `error_message` | `TEXT` | 最近错误消息，可为空 |
| `error_details` | `JSON` | 最近错误详情，可为空 |
| `attempt_count` | `INT UNSIGNED` | 默认 0 |
| `lock_version` | `INT UNSIGNED` | 乐观锁，默认 1 |

#### users

M1 建立最小登录用户表，角色固定为 `ADMIN` 与 `USER`，不提供注册接口。

| 字段 | 类型 | 约束与说明 |
|---|---|---|
| `id` | `CHAR(36)` | 主键 UUID |
| `username` | `VARCHAR(64)` | 唯一、非空登录名 |
| `password_hash` | `VARCHAR(255)` | Argon2 密码哈希，绝不保存明文 |
| `role` | `VARCHAR(16)` | `ADMIN` 或 `USER` |
| `is_active` | `BOOLEAN` | 停用后不能签发或使用令牌 |
| `created_at`、`updated_at` | `DATETIME(6)` | UTC 时间 |

部署时种子程序从 `SEED_ADMIN_*` 与 `SEED_USER_*` 环境变量创建管理员和普通用户。重复运行只确保账号存在、角色正确且启用，不覆盖已有密码。

#### calculation_attempts

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `CHAR(36)` | 主键 UUID |
| `record_id` | `CHAR(36)` | 外键关联 `calculation_records.id` |

| `execution_id` | `CHAR(36)` | 对外执行幂等标识，唯一 |

#### achievement_records

数据 MVP 的统一成果记录。各来源数据保留在 `payload`，但必须先经过审核；后续计算服务仅查询 `status=approved` 的记录。

| 字段 | 类型 | 说明 |
|---|---|---|
| `teacher_id`、`teacher_name` | `VARCHAR` | 教师稳定标识及显示名称 |
| `department_id` | `VARCHAR(64)` | 院系标识，后续关联组织表 |
| `achievement_type`、`level` | `VARCHAR` | 成果类别与等级 |
| `occurred_at` | `DATE` | 成果发生日期 |
| `source`、`source_record_id` | `VARCHAR` | 来源与来源内唯一记录标识 |
| `payload` | `JSON` | 类型特有的原始数据 |
| `status` | `VARCHAR(32)` | `pending_review/approved/rejected` |
| 审核字段 | 用户 ID、时间、意见 | 审核结论的可追溯信息 |

唯一约束：`uk_achievement_source_record(source, source_record_id)`；索引覆盖审核队列、教师和院系查询。

#### function_definitions 与 function_versions

| 表 | 核心字段 | 作用 |
|---|---|---|
| `function_definitions` | `id`、`name`、`kind`、`status`、`description` | 函数稳定标识与启停状态 |
| `function_versions` | `id`、`function_id`、`version`、`input_schema`、`output_schema`、`executor_id`、`is_active` | 可执行版本与 JSON Schema 契约 |

唯一约束：函数名唯一；同一函数内版本号唯一。历史版本不可覆盖或删除，只能停用新建记录的引用。

| `calculation_batches` | 一次按周期或范围发起的计算批次 | 第二阶段 |
| `executors` | 外部执行器标识、状态、超时和凭证引用 | 第二阶段 |
| `record_links` | 跨表数据引用和执行依赖 | 第四阶段 |
| `rule_plugins` | 插件版本、函数引用、默认输入与启停状态 | 已完成 |
| `workflow_definitions`、`workflow_nodes` | 工作流定义、有序节点与冻结插件快照 | 已完成 |
| `workflow_runs`、`workflow_run_nodes` | 工作流运行、节点输入/输出/错误快照与计算记录关联 | 已完成 |
| `roles`、`user_roles` | 细粒度角色与权限 | 第三阶段 |
| `organizations` | 学校、学院和部门范围 | 第三阶段 |
| `audit_logs` | 规则、执行、重试、导出审计 | 第三阶段 |

### 7.3 DDL 示例

```sql
CREATE TABLE calculation_records (
  id CHAR(36) NOT NULL,
  table_name VARCHAR(64) NOT NULL,
  period_id VARCHAR(64) NULL,
  input_data JSON NOT NULL,
  function_spec JSON NOT NULL,
  output_data JSON NULL,
  status VARCHAR(16) NOT NULL,
  error_code VARCHAR(64) NULL,
  error_message TEXT NULL,

```

## 8. 安全、权限与审计

M1 已实现基础登录：预置 `ADMIN` 与 `USER` 用户使用用户名、密码和 JWT 认证；不提供注册接口。令牌中含用户 ID、用户名和角色，服务端每次访问受保护资源时仍查询用户启用状态。数据 MVP 中，`ADMIN` 暂时同时承担系统导入与院系审核职责；当前尚未按 `department_id` 限制管理员数据范围。正式使用前扩展数据范围和细粒度角色权限。

| 角色 | 最小权限 |
|---|---|
| `ADMIN` | M1 管理员身份；后续承接函数、执行器、组织、用户和全局配置管理 |
| `USER` | M1 普通身份；后续按数据范围授予记录和结果访问权限 |

安全要求：

- API 使用 HTTPS，生产环境不得暴露 MySQL 端口到公网；
- 密码、JWT 密钥和外部执行器令牌存入环境变量或密钥管理服务；
- 所有记录写入、执行、重载、重试、函数版本修改和导出均写入 `audit_logs`；
- Function 字段只接受白名单 JSON 结构；
- 外部执行器使用 allowlist、超时、服务凭证和响应 Schema 校验；
- 使用参数化查询和 ORM，禁止拼接 SQL；
- 对错误响应进行脱敏，不将堆栈和密钥返回给调用方。

## 9. 环境部署

### 9.1 开发环境

要求：本机 MySQL 8.0 与 Python 3.12。开发环境默认直接连接本机 MySQL，应用在虚拟环境中运行；Docker Compose 仅保留为可选的隔离环境方案。

```text
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_DATABASE=numcounts
MYSQL_USER=numcounts_app
MYSQL_PASSWORD=<本地开发密码>
DATABASE_URL=mysql+asyncmy://numcounts_app:<密码>@127.0.0.1:3306/numcounts
APP_ENV=development
LOG_LEVEL=INFO
JWT_SECRET=<本地开发密钥>
SEED_ADMIN_USERNAME=admin
SEED_ADMIN_PASSWORD=<管理员初始密码>
SEED_USER_USERNAME=user
SEED_USER_PASSWORD=<普通用户初始密码>
```

启动顺序：

1. 启动本机 MySQL 并确认 `numcounts` 数据库可连接；
2. 执行 `alembic upgrade head`；
3. 运行 `python -m app.db.seed` 创建初始 `ADMIN` 与 `USER` 账号；
4. 内置函数由应用内只读注册表提供，无需写入函数种子数据；
5. 启动 FastAPI API 服务；
6. 启动单线程执行器；
7. 运行接口测试和两表三规则验收场景。

### 9.2 Docker Compose 组件

| 服务 | 镜像或构建来源 | 职责 |
|---|---|---|
| `mysql` | `mysql:8.0` | 持久化数据 |
| `migrate` | 项目 Dockerfile | 执行 Alembic 迁移 |
| `seed` | 项目 Dockerfile | 创建或校正初始登录账号 |
| `api` | 项目 Dockerfile | FastAPI HTTP 服务 |
| `worker` | 项目 Dockerfile | 单线程执行器进程 |
| `nginx` | `nginx:alpine` | 反向代理与 TLS 终止 |
| `redis` | `redis:7-alpine` | 可选缓存与未来锁服务 |

`api` 和 `worker` 使用相同应用镜像，但分别以 API 和执行器命令启动。MVP 保持 `worker` 副本数为 1，确保执行顺序确定；扩展并发前必须完成记录锁和并发测试。

### 9.3 生产环境

- MySQL 使用主从或托管高可用实例，启用自动备份、慢查询日志和监控；
- API 至少部署两个副本并通过负载均衡访问；
- 执行器初期只部署一个副本；
- Nginx 或云负载均衡负责 TLS，FastAPI 仅接受内网流量；
- 使用 CI/CD 执行测试、构建镜像、运行 Alembic 迁移、滚动发布和健康检查；
- 生产迁移需先备份数据库，并在预发布环境验证迁移与回滚策略；
- 记录、执行历史和审计日志设定保留期限与归档策略，满足学校数据管理要求。

### 9.4 健康检查与监控

| 项目 | 指标或检查 |
|---|---|
| API 存活 | `/api/v1/health/live` |
| 服务就绪 | `/api/v1/health/ready`，检查 MySQL 连接 |
| 执行积压 | `pending` 记录数与最早等待时间 |
| 执行成功率 | 按函数、表、周期统计成功与失败次数 |
| 外部执行器 | 响应耗时、超时率和错误码分布 |
