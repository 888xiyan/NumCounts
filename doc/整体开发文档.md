# NumCounts 整体开发文档

## 1. 项目目标

NumCounts 是一个面向高校绩效核算的可配置计算系统。系统将绩效规则、业务输入和计算结果保存为表记录，由计算核心按统一契约执行。插件用于封装复杂计算，工作流用于面向操作员编排导入、校验、计算、复核和导出。

第一目标是建立可靠的计算语义：相同输入、函数版本和执行方式必须得到可追溯的结果；规则错误必须不影响无关记录；重试必须只作用于指定记录。

## 4. 核心模型

### 4.1 记录

一条记录代表一次可执行的绩效计算单元。

```json
{
  "id": "rec_01J...",
  "table_name": "teaching_rules",
  "input": {
    "hours": 36,
    "rate": 80,
    "quality_factor": 1.1
  },
  "function": {
    "kind": "registered",
    "name": "teaching_performance",
    "version": "1.0.0"
  },
  "output": null,
  "status": "pending",
  "error": null,
  "attempt_count": 0
}
```

| 业务字段 | 作用 | 写入方 |
|---|---|---|
| `input` | 函数所需的业务输入 | 外部调用方，经核心校验 |
| `function` | 函数类型、名称与版本 | 外部调用方，经核心路由校验 |
| `output` | 成功计算结果 | 仅计算核心 |

| 执行元数据 | 作用 |
|---|---|
| `id` | 记录稳定标识 |
| `table_name` | 记录所属逻辑表 |
| `status` | 当前生命周期状态 |
| `error` | 最近一次失败原因 |
| `attempt_count` | 已发起的执行次数 |
| `created_at`、`updated_at` | 创建与最近变更时间 |

### 4.2 Function 规则

`Function` 是 JSON 描述对象，不是可直接执行的 Python 或 JavaScript 源码。

当前仅支持内置函数引用：

```json
{
  "kind": "registered",
  "name": "teaching_performance",
  "version": "1.0.0"
}
```

核心按照 `(name, version)` 查找函数。未知函数会在创建时返回 `404 FUNCTION_NOT_FOUND`；输入错误会在执行时写入失败记录。禁止把源码、Shell 指令、数据库语句或任意 URL 写入 `Function`。

后续外部执行器使用以下形式：

```json
{
  "kind": "external",
  "executor_id": "research-policy-runner",
  "name": "calculate_paper_performance",
  "version": "2.1.0"
}
```

`executor_id` 由核心映射到部署配置中的可信服务地址和凭证，记录本身不能指定地址或认证信息。

### 4.3 状态机

```text
创建记录                  → pending
执行：pending/success/failed → running → success 或 failed
局部重载：success/failed/pending → pending
重试：success/failed/pending → pending → running → success 或 failed
```

- `run_pending()` 只读取 `pending` 记录，并按创建时间顺序执行。
- 每次实际执行尝试均增加 `attempt_count`。
- `reload_record(record_id)` 清除指定记录的输出和错误，并恢复为 `pending`。
- `retry_record(record_id)` 依次执行局部重载和执行。
- `running` 状态禁止重复执行与重载。
- 一条记录失败不会中断其他待执行记录。

当前不支持插队、批量重载、自动重试、跨记录状态传播和跨表依赖调度。

## 6. 外部接口设计

FastAPI 服务已提供正式计算记录 API，并保持与 Python 内核相同的语义。

数据 API 已先行完成。导入和手工申报均进入 `pending_review`，`ADMIN` 审核为 `approved` 后，后续计算记录只能从可计算成果查询读取输入；详细约束见 [数据MVP设计.md](数据MVP设计.md)。

| 操作 | HTTP 接口 | 核心方法 | 结果 |
|---|---|---|---|
| 创建记录 | `POST /v1/records` | `create_record()` | 返回 `pending` 记录 |
| 执行记录 | `POST /v1/records/{id}/execute` | `run_record()` | 返回成功输出或失败错误 |
| 执行待处理记录 | `POST /v1/records/run-pending` | `run_pending()` | 返回本轮执行记录 |
| 查询记录 | `GET /v1/records/{id}` | `get_record()` | 返回完整记录 |
| 查询列表 | `GET /v1/records` | `list_records()` | 按表名、状态过滤 |
| 局部重载 | `POST /v1/records/{id}/reload` | `reload_record()` | 返回恢复为待执行的记录 |
| 重试记录 | `POST /v1/records/{id}/retry` | `retry_record()` | 返回新一次执行后的记录 |

创建请求必须使用 `Content-Type: application/json`，并携带 `Idempotency-Key`。HTTP 适配层需将同一幂等键和相同请求体映射到同一记录；同一键且请求体不同返回冲突错误。

完整的请求、响应、错误码和外部执行器协议见 [计算核心MVP设计.md](计算核心MVP设计.md)。

## 7. 外部输入契约

### 7.1 通用输入约束

| 项目 | 要求 |
|---|---|
| 表名 | 小写字母、数字与下划线组成，建议使用业务复数名，如 `teaching_rules` |
| 输入类型 | 仅 JSON 原生对象、数组、字符串、数值、布尔值和空值 |
| 输入大小 | MVP 上限 64 KiB |
| 金额与系数 | 使用 JSON 数值；展示层统一处理格式化 |
| 日期时间 | UTC ISO 8601 字符串 |
| 函数 | 必须是已登记的名称和版本 |
| 禁止内容 | 源码、任意 URL、凭证、二进制对象和数据库指令 |

### 7.2 当前函数输入

| 函数 | 必填输入 | 成功输出 |
|---|---|---|
| `teaching_performance@1.0.0` | `hours`、`rate` 非负；可选 `quality_factor` | `amount = hours × rate × quality_factor` |
| `course_bonus@1.0.0` | `course_count` 非负整数，`level` 为 `national`、`provincial` 或 `school` | 对应固定奖励金额 |
| `research_performance@1.0.0` | `papers`、`projects`、`funding` 与可选权重均非负 | 分项汇总金额 |

输入缺失、无法转换为数值、数值为负或枚举值无效时，函数抛出业务错误。核心将错误写入记录并将状态置为 `failed`。

## 8. 外部业务执行器设计

复杂规则不应被塞入记录字段，而应由独立执行器实现。核心调用执行器时传递稳定的执行标识、记录标识、函数引用和输入。

```json
{
  "execution_id": "exec_01J...",
  "record_id": "rec_01J...",
  "table_name": "research_rules",
  "function": {
    "name": "calculate_paper_performance",
    "version": "2.1.0"
  },
  "input": {
    "paper_level": "A",
    "author_rank": 1,
    "author_count": 3
  },
  "timeout_ms": 5000
}
```

执行器只能返回以下两类响应：

```json
{"status":"success","output":{"amount":12000}}
```

```json
{
  "status": "failed",
  "error": {
    "code": "INVALID_AUTHOR_RANK",
    "message": "author_rank must be between 1 and author_count",
    "retryable": false
  }
}
```

核心负责超时、认证失败和无效响应的统一错误转换；执行器不得自行修改核心数据库或记录状态。相同 `execution_id` 必须幂等。

## 9. 当前验收场景

| 表 | 规则 | 输入 | 首次执行 | 重试 |
|---|---|---|---|---|
| `teaching_rules` | 课时绩效 | `36 × 80 × 1.1` | 成功，`3168.0` | 不执行 |
| `teaching_rules` | 精品课程奖励 | `level=municipal` | 失败，`INVALID_FUNCTION_INPUT` | 局部重试后仍失败，尝试次数为 `2` |
| `research_rules` | 科研绩效 | `papers=2`、`projects=1`、`funding=10000` | 成功 | 不执行 |

验收条件：两条成功记录保存结果；失败记录保存错误；失败记录局部重试后继续报告错误；两条成功记录的尝试次数保持为 `1`。

运行示例：

```bash
python3 -m demo.demo --database /tmp/numcounts-demo.db
```

运行测试：

```bash
python3 -m unittest -v
```

## 10. 开发阶段与交付标准

### 阶段一 最小内核

**目标：** 固化记录、函数、输出、状态和局部重试语义。

**已交付：** SQLite 原型及 FastAPI/MySQL 正式实现：JSON Function、三类内置函数、单线程执行、错误保存、局部重载、重试、尝试历史、迁移和自动测试。

**完成标准：** 当前验收场景与全部自动化测试通过。

### 阶段二 服务接口与外部执行

**目标：** 让外部系统以稳定协议使用内核，并将复杂规则从核心进程中拆出。

**已完成：** FastAPI 计算记录接口、JWT 权限、请求校验、幂等键、函数目录、MySQL 执行尝试记录、两表三规则端到端验收，以及外部执行器的受控登记、认证、超时、响应校验和契约测试。

**完成标准：** 两表三规则场景可通过 HTTP 完成；外部执行器的成功、业务失败、超时、认证失败和无效响应均会写入正确的执行结果或错误。

### 阶段三 规则插件与工作流

**目标：** 让规则管理员与绩效操作员无需改动核心代码即可完成核算。

**交付项：**

- 插件清单、函数元数据、版本冻结和启停；
- Excel 或 CSV 输入导入、字段映射和错误行报告；
- 工作流定义、节点状态和执行记录；
- 工作流编辑器生成底层记录，不直接存储独立逻辑；
- 结果汇总、明细追溯和导出。

**完成标准：** 操作员可完成一次数据导入、规则选择、计算、错误处理、复核和结果导出；每个输出可回溯到输入和函数版本。

### 阶段四 跨表链接与运行治理

**目标：** 支持复杂绩效规则的显式依赖和可靠运行。

**交付项：**

- 显式跨表数据引用与执行依赖；
- 依赖图校验、循环检测和等待状态；
- 结果版本冻结和可控失效标记；
- 身份认证、角色权限、组织范围控制；
- 操作日志、审计事件、指标监控与告警；
- 异常恢复和备份策略。

**完成标准：** 链接关系可追溯，循环依赖被拒绝，权限和审计覆盖规则、执行、重载、导出等关键操作。

### 阶段五 性能与内核演进

**目标：** 在不改变记录与执行契约的前提下提高吞吐和稳定性。

**交付项：**

- 调度性能压测与瓶颈分析；
- 可控并发执行与并发安全测试；
- 任务队列与运行监控；
- 必要时将状态机和调度内核迁移至 Go；
- Python 插件和外部 API 契约保持兼容。

**完成标准：** 性能、恢复能力和兼容性达到目标规模，迁移前后同一记录样本得到等价结果。

## 11. 测试与质量要求

| 测试层级 | 覆盖内容 |
|---|---|
| 函数单元测试 | 必填字段、数值范围、金额计算、枚举校验 |
| 内核单元测试 | 创建、执行、失败、状态转换、局部重载与重试 |
| 数据库迁移测试 | 旧 `function_name` 数据迁移至 `function_json` |
| API 集成测试 | 请求校验、幂等、并发冲突、错误响应 |
| 执行器契约测试 | 成功、业务失败、超时、认证失败、无效响应 |
| 端到端测试 | 导入到导出、追溯链路和权限范围 |

每增加一种函数或插件，都必须提供成功、输入错误和版本不匹配三类测试。每个缺陷修复均应先增加能稳定复现该问题的测试。

## 12. 关键决策与风险控制

| 决策 | 原因 | 约束 |
|---|---|---|
| Function 使用 JSON 引用 | 保证安全、版本化和跨语言迁移 | 不执行字段内源码 |
| SQLite 原型与 MySQL 正式存储 | 原型快速验证，正式服务持久化与事务控制 | 后续根据规模评估架构 |
| 单线程执行 | 先确保状态机与失败语义正确 | 后续并发不改变接口语义 |
| 局部重载 | 避免错误扩散并简化审计 | 暂不传播下游失效状态 |
| 外部执行器受控登记 | 允许复杂业务扩展 | 记录不可指定任意 URL 或凭证 |
| 显式重试 | 保持失败与重试可追溯 | MVP 不自动重试 |

## 13. 下一步开发顺序

1. 将已审核成果按周期映射为计算记录，并增加批次与结果导出。
2. 建立函数版本持久化、审计日志和组织数据范围。
3. 增加插件与工作流操作界面，始终以底层表记录为事实来源。
4. 再引入跨表链接、依赖图和版本冻结，不在此之前增加插队与并发调度。
