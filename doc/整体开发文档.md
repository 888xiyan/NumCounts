# NumCounts 整体开发文档

## 1. 项目目标

NumCounts 是一个面向高校绩效核算的可配置计算系统。系统将绩效规则、业务输入和计算结果保存为表记录，由计算核心按统一契约执行。插件用于封装复杂计算，工作流用于面向操作员编排导入、校验、计算、复核和导出。

第一目标是建立可靠的计算语义：相同输入、函数版本和执行方式必须得到可追溯的结果；规则错误必须不影响无关记录；重试必须只作用于指定记录。

## 4. 核心模型

### 4.1 记录

一条记录代表一次可执行的绩效计算单元。

```json
{
  "id": "rec_01J...",
  "table_name": "teaching_rules",
  "input": {
    "hours": 36,
    "rate": 80,
    "quality_factor": 1.1
  },
  "function": {
    "kind": "registered",
    "name": "teaching_performance",
    "version": "1.0.0"
  },
  "output": null,
  "status": "pending",
  "error": null,
  "attempt_count": 0
}
```

| 业务字段 | 作用 | 写入方 |
|---|---|---|
| `input` | 函数所需的业务输入 | 外部调用方，经核心校验 |
| `function` | 函数类型、名称与版本 | 外部调用方，经核心路由校验 |
| `output` | 成功计算结果 | 仅计算核心 |

| 执行元数据 | 作用 |
|---|---|
| `id` | 记录稳定标识 |
| `table_name` | 记录所属逻辑表 |
| `status` | 当前生命周期状态 |
| `error` | 最近一次失败原因 |
| `attempt_count` | 已发起的执行次数 |
| `created_at`、`updated_at` | 创建与最近变更时间 |

### 4.2 Function 规则

`Function` 是 JSON 描述对象，不是可直接执行的 Python 或 JavaScript 源码。

当前仅支持内置函数引用：

```json
{
  "kind": "registered",
  "name": "teaching_performance",
  "version": "1.0.0"
}
```

核心按照 `(name, version)` 查找函数。未知函数会在创建时返回 `404 FUNCTION_NOT_FOUND`；输入错误会在执行时写入失败记录。禁止把源码、Shell 指令、数据库语句或任意 URL 写入 `Function`。

外部执行器使用以下形式：

```json
{
  "kind": "external",
  "executor_id": "research-policy-runner",
  "name": "calculate_paper_performance",
  "version": "2.1.0"
}
```

`executor_id` 由核心映射到部署配置中的可信服务地址和凭证，记录本身不能指定地址或认证信息。

### 4.3 状态机

```text
创建记录                  → pending
执行：pending/success/failed → running → success 或 failed
局部重载：success/failed/pending → pending
重试：success/failed/pending → pending → running → success 或 failed
```

- `run_pending()` 只读取 `pending` 记录，并按创建时间顺序执行。
- 每次实际执行尝试均增加 `attempt_count`。
- `reload_record(record_id)` 清除指定记录的输出和错误，并恢复为 `pending`。
- `retry_record(record_id)` 依次执行局部重载和执行。
- `running` 状态禁止重复执行与重载。
- 一条记录失败不会中断其他待执行记录。

当前不支持插队、批量重载、自动重试、跨表动态查询、分支工作流和并发依赖调度。

## 6. 外部接口设计

FastAPI 服务已提供正式计算记录 API，并保持与 Python 内核相同的语义。

数据 API 已先行完成。导入和手工申报均进入 `pending_review`，`ADMIN` 审核为 `approved` 后，后续计算记录只能从可计算成果查询读取输入；详细约束见 [数据MVP设计.md](数据MVP设计.md)。

| 操作 | HTTP 接口 | 核心方法 | 结果 |
|---|---|---|---|
| 创建记录 | `POST /v1/records` | `create_record()` | 返回 `pending` 记录 |
| 执行记录 | `POST /v1/records/{id}/execute` | `run_record()` | 返回成功输出或失败错误 |
| 执行待处理记录 | `POST /v1/records/run-pending` | `run_pending()` | 返回本轮执行记录 |
| 查询记录 | `GET /v1/records/{id}` | `get_record()` | 返回完整记录 |
| 查询列表 | `GET /v1/records` | `list_records()` | 按表名、状态过滤 |
| 局部重载 | `POST /v1/records/{id}/reload` | `reload_record()` | 返回恢复为待执行的记录 |
| 重试记录 | `POST /v1/records/{id}/retry` | `retry_record()` | 返回新一次执行后的记录 |

创建请求必须使用 `Content-Type: application/json`，并携带 `Idempotency-Key`。HTTP 适配层需将同一幂等键和相同请求体映射到同一记录；同一键且请求体不同返回冲突错误。

完整的请求、响应、错误码和外部执行器协议见 [计算核心MVP设计.md](计算核心MVP设计.md)。

## 7. 外部输入契约

### 7.1 通用输入约束

| 项目 | 要求 |
|---|---|
| 表名 | 小写字母、数字与下划线组成，建议使用业务复数名，如 `teaching_rules` |
| 输入类型 | 仅 JSON 原生对象、数组、字符串、数值、布尔值和空值 |
| 输入大小 | MVP 上限 64 KiB |
| 金额与系数 | 使用 JSON 数值；展示层统一处理格式化 |
| 日期时间 | UTC ISO 8601 字符串 |
| 函数 | 必须是已登记的名称和版本 |
| 禁止内容 | 源码、任意 URL、凭证、二进制对象和数据库指令 |

### 7.2 当前函数输入

| 函数 | 必填输入 | 成功输出 |
|---|---|---|
| `teaching_performance@1.0.0` | `hours`、`rate` 非负；可选 `quality_factor` | `amount = hours × rate × quality_factor` |
| `course_bonus@1.0.0` | `course_count` 非负整数，`level` 为 `national`、`provincial` 或 `school` | 对应固定奖励金额 |
| `research_performance@1.0.0` | `papers`、`projects`、`funding` 与可选权重均非负 | 分项汇总金额 |

输入缺失、无法转换为数值、数值为负或枚举值无效时，函数抛出业务错误。核心将错误写入记录并将状态置为 `failed`。

## 8. 外部业务执行器设计

复杂规则不应被塞入记录字段，而应由独立执行器实现。核心调用执行器时传递稳定的执行标识、记录标识、函数引用和输入。

```json
{
  "execution_id": "exec_01J...",
  "record_id": "rec_01J...",
  "table_name": "research_rules",
  "function": {
    "name": "calculate_paper_performance",
    "version": "2.1.0"
  },
  "input": {
    "paper_level": "A",
    "author_rank": 1,
    "author_count": 3
  },
  "timeout_ms": 5000
}
```

执行器只能返回以下两类响应：

```json
{"status":"success","output":{"amount":12000}}
```

```json
{
  "status": "failed",
  "error": {
    "code": "INVALID_AUTHOR_RANK",
    "message": "author_rank must be between 1 and author_count",
    "retryable": false
  }
}
```

核心负责超时、认证失败和无效响应的统一错误转换；执行器不得自行修改核心数据库或记录状态。相同 `execution_id` 必须幂等。

## 9. 当前验收场景

| 表 | 规则 | 输入 | 首次执行 | 重试 |
|---|---|---|---|---|
| `teaching_rules` | 课时绩效 | `36 × 80 × 1.1` | 成功，`3168.0` | 不执行 |
| `teaching_rules` | 精品课程奖励 | `level=municipal` | 失败，`INVALID_FUNCTION_INPUT` | 局部重试后仍失败，尝试次数为 `2` |
| `research_rules` | 科研绩效 | `papers=2`、`projects=1`、`funding=10000` | 成功 | 不执行 |

验收条件：两条成功记录保存结果；失败记录保存错误；失败记录局部重试后继续报告错误；两条成功记录的尝试次数保持为 `1`。

运行示例：

```bash
python3 -m demo.demo --database /tmp/numcounts-demo.db
```

运行测试：

```bash
python3 -m unittest -v
```

## 10. 开发阶段与交付标准

### 阶段一 最小内核

**目标：** 固化记录、函数、输出、状态和局部重试语义。

**已交付：** SQLite 原型及 FastAPI/MySQL 正式实现：JSON Function、四类内置函数、单线程执行、错误保存、局部重载、重试、尝试历史、迁移和自动测试。

**完成标准：** 当前验收场景与全部自动化测试通过。

### 阶段二 服务接口与外部执行

**目标：** 让外部系统以稳定协议使用内核，并将复杂规则从核心进程中拆出。

**已完成：** FastAPI 计算记录接口、JWT 权限、请求校验、幂等键、函数目录、MySQL 执行尝试记录、两表三规则端到端验收，以及外部执行器的受控登记、认证、超时、响应校验和契约测试。

**完成标准：** 两表三规则场景可通过 HTTP 完成；外部执行器的成功、业务失败、超时、认证失败和无效响应均会写入正确的执行结果或错误。

### 阶段三 规则插件与工作流

**目标：** 让规则管理员与绩效操作员无需改动核心代码即可完成核算。

**已完成：** 版本化插件目录、启停、函数与默认输入快照；插件引用计算记录；工作流草稿/启用/停用；插件计算节点和金额汇总节点；工作流运行、节点状态、错误快照与底层计算记录关联；无需构建工具的本地操作员工作台。

**完成标准：** 管理员能配置并启用插件和顺序工作流；一次运行可从上下文构造输入、执行多个计算节点、汇总 `amount`，并对每个节点追溯输入、输出、错误和计算记录。详细约定见 [规则插件与工作流设计.md](规则插件与工作流设计.md)。

### 阶段四 跨表链接与运行治理（权限相关任务挂起）

**目标：** 支持复杂绩效规则的显式依赖和可靠运行。

**已完成：** 显式 `data` / `execution` 跨表链接、依赖图循环拒绝、`waiting` 等待状态、链接与目标版本快照、下游 `stale` 标记、运行中断恢复、审计事件和运行指标接口。

**挂起：** 身份认证改造、细粒度角色权限和组织范围控制。本阶段不改动既有 `ADMIN` / `USER` 授权模型。

**完成标准：** 链接关系、执行输入和目标版本可追溯；循环依赖被拒绝；目标变更不会静默覆盖下游历史结果；中断记录可恢复为可重试失败状态。详细约定见 [跨表链接与运行治理设计.md](跨表链接与运行治理设计.md)。

### 阶段五 性能与内核演进

**目标：** 在不改变记录与执行契约的前提下提高吞吐和稳定性。

**交付项：**

- 调度性能压测与瓶颈分析；
- 可控并发执行与并发安全测试；
- 任务队列与运行监控；
- 必要时将状态机和调度内核迁移至 Go；
- Python 插件和外部 API 契约保持兼容。

**完成标准：** 性能、恢复能力和兼容性达到目标规模，迁移前后同一记录样本得到等价结果。

## 12. 关键决策与风险控制

| 决策 | 原因 | 约束 |
|---|---|---|
| Function 使用 JSON 引用 | 保证安全、版本化和跨语言迁移 | 不执行字段内源码 |
| SQLite 原型与 MySQL 正式存储 | 原型快速验证，正式服务持久化与事务控制 | 后续根据规模评估架构 |
| 单线程执行 | 先确保状态机与失败语义正确 | 后续并发不改变接口语义 |
| 局部重载 | 避免错误扩散并简化审计 | 暂不传播下游失效状态 |
| 外部执行器受控登记 | 允许复杂业务扩展 | 记录不可指定任意 URL 或凭证 |
| 显式重试 | 保持失败与重试可追溯 | MVP 不自动重试 |

## 13. 最新业务基线下的开发计划

本节是当前后续开发的主路线，优先级高于前文面向早期内核建设的阶段描述。M0—M3、跨表链接与运行治理已完成；后续围绕管理员正式计算和成员自助边界推进。没有明确项目日历时不预设交付日期，按依赖和验收门槛排期。

### M4 函数快照与正式计算基础（P0）

**目标：** 让管理员正式计算的每个结果能够对应当时的实际函数本体、输入和版本快照。

**交付内容（已实现，本地开发库迁移已执行）：**

1. 先确定函数本体的受控快照格式、来源、保存位置、依赖锁定与摘要校验策略；禁止任意代码执行。
2. 扩展计算尝试快照，使其保存实际执行函数本体及内容摘要，而不只保存函数引用、函数元数据或插件 JSON。
3. 记录执行人、计算周期、输入、规则/插件/工作流版本、输出、错误和审核/运行关联。
4. 为新旧计算记录定义兼容语义：旧记录注明其仅保存引用；新正式计算必须具备函数本体快照。

**验收：** 管理员正式计算可从历史记录读取当次输入、输出和函数本体；快照摘要可校验；更改或停用当前函数/插件不会改变历史记录内容；执行仍受注册表或等价受控执行策略限制。

### M5 管理员正式绩效核算闭环（P0）

**目标：** 把已审核成果、周期、工作流和计算记录连接成正式核算批次。

**工作项：**

1. 明确并实现核算批次、人员范围、周期、正式结果与明细的业务关联。
2. 将仅 `approved` 的成果映射为工作流上下文和计算输入；保留成果来源与去重记录。
3. 管理员发起基础绩效计算，结果落入正式结果域；支持复核前后状态、异常定位和结果导出所需的数据接口。
4. 记录发起人、执行时间、工作流/插件版本、函数本体、结果版本及必要审计事件。
5. 明确重新计算生成新结果版本的方式；不覆盖历史正式计算。正式结果撤回、审批层级等未决规则先列为决策项。

**验收：** 管理员可从已审核成果发起一个有周期和人员范围的批次；成功和失败均可追溯；每个正式输出关联实际函数本体；重新计算保留历史版本；未审核成果不能进入批次。

### M6 成员使用、个人结果与导出（P0）

**目标：** 让成员使用管理员发布的能力，同时保证成员运行不改变正式绩效。

**工作项：**

1. 扩展授权：管理员可以创建/修改/发布插件和工作流；成员只能读取可用定义并执行获准的工作流。
2. 建立成员运行与正式运行的隔离标记、持久化边界和本人数据访问校验。成员结果进入暂存，不写入正式绩效结果表或核算批次。
3. 提供成员个人正式绩效查询和明细追溯，只能访问本人数据。
4. 提供本人绩效及允许字段的导出；导出记录用户、时间和来源结果版本。
5. 实现成员暂存的查看、删除和过期清理前，先确认保存内容、保留期限、管理员可见性等待定规则。

**验收：** 成员能使用已发布插件/工作流，暂存和导出自己的试算，但不能修改定义、触发正式落库或读取他人结果；正式绩效查询与导出只返回本人正式版本。

### M7 特殊绩效审核与申诉闭环（P1）

**目标：** 将特殊绩效申请和对正式个人绩效的申诉分成可审核、可追溯的业务流程。

**已确认口径：** 特殊绩效与申诉是需要材料提交和审批的复杂绩效事项。材料随流程保存，草稿可修改、提交后冻结；事项按 `draft → submitted → reviewing → approved → processed` 流转，审核打回或专用插件失败回到草稿。处理人与复核人使用独立接口，当前均临时绑定 `ADMIN`；默认时限为三天，时限修改接口也暂时绑定 `ADMIN`。通知只预留接口，不实现发送。

**工作项：**

1. 建立特殊绩效申请和绩效申诉的数据模型，关联成员、申诉原正式结果版本、材料版本、提交快照、处理人和复核人。
2. 提供成员草稿、材料、提交和本人进度查询接口；提交后拒绝成员修改，仅在打回草稿后允许再次编辑。
3. 提供管理员受理、处理、复核、打回和时限调整接口，并记录意见、原因和三天时限的调整轨迹。
4. 审核通过后以冻结快照调用专用插件，生成关联申请的 `approved` 成果来源；管理员重新发起正式核算生成新结果版本，不覆盖旧结果。
5. 预留通知服务事件和接口，不实现消息投递；完善权限检查、审计和双端页面。

**验收：** API、成员/管理员操作台和专项测试已覆盖事项创建、材料冻结、受理、复核、插件失败回草稿及审计；正式结果仍须通过 M5 新版本重算，旧结果不覆盖。本地开发库已执行 M7 迁移；其他环境升级后才能启用此能力。
