# M8 业务验收与运行手册

本文用于 M8 的业务闭环验收、运行观察、备份恢复演练与容量测量。它描述操作步骤和验收证据，不代表生产备份、告警或恢复演练已经执行。

## 1. 当前边界与前置条件

- 后端使用 FastAPI、SQLAlchemy 和 MySQL；当前执行器是单线程轮询进程。
- 本地开发库 `numcounts` 已在用户明确授权后升级到 Alembic `20261020_0011`。其他环境仍须按各自变更流程备份和授权迁移；本文不授权操作其他环境。
- 身份认证仍按当前 `ADMIN` / `USER` 行为验收。更细角色、组织数据范围仍挂起。
- M8 暂无已确认的吞吐量、响应时间或数据规模目标。先测量并记录基线，再由业务与运维负责人共同确认目标和告警阈值。
- 验收与恢复数据应为合成数据或已批准的脱敏数据；不得将备份文件放入代码仓库。

## 2. 业务端到端验收

每次验收记录环境、版本、周期、操作者、请求 ID、批次 ID、结果 ID、事项 ID、截图或脱敏响应，以及通过/失败结论。不得在记录中包含密码、JWT 或材料原文。

### 2.1 成果审核到正式结果

1. 准备已绑定 `teacher_id` 的 `USER` 和一个 `ADMIN` 测试账号，使用隔离的验收数据库。
2. 由 `USER` 手工申报一项成果，确认初始状态为 `pending_review`，且不可计入正式计算。
3. 由 `ADMIN` 审核通过。用 `GET /api/v1/achievements/eligible` 确认仅审核通过成果进入可计算输入。
4. 由 `ADMIN` 创建正式核算批次，确认批次、工作流快照、成果来源快照和结果版本均可查询。
5. 复核批次，确认其状态转为 `reviewed`；再以 `USER` 查询 `/api/v1/me/formal-calculation-results` 并导出本人结果。
6. 尝试查询另一个教师的结果；必须被服务端范围约束拦截。以 `ADMIN` 导出批次或周期结果，确认导出审计存在。
7. 对同一教师和周期再次计算，确认产生更高的 `result_version`，旧版本仍可查且未被覆盖。

### 2.2 特殊绩效 / 申诉闭环

验收目标必须包含 M7 迁移 `20261020_0011`；当前本地开发库已满足此条件。

1. `USER` 创建特殊绩效草稿，上传材料并提交；确认提交后表单及材料版本冻结、截止时间默认三天。
2. `ADMIN` 受理、复核通过并选择 `purpose=special_case` 插件；确认所有状态变更及处理/复核人均可追溯。
3. 运行专用插件。成功时确认生成关联的 `approved` 成果来源，而不是直接写入正式结果；失败时确认事项回到草稿并保留错误记录。
4. 将已批准的成果纳入新的正式核算批次并复核。确认新结果版本包含来源快照，旧版本仍保留。
5. 验证用户提交后不能修改材料；打回草稿后允许再次修改；通知只记录请求事件，不实际发送。

## 3. 运行诊断与告警接入

### 3.1 检查点

| 检查 | 接口或信号 | 判读方式 |
|---|---|---|
| API 存活 | `GET /api/v1/health/live` | 进程可响应；不代表数据库可用 |
| 服务就绪 | `GET /api/v1/health/ready` | MySQL `SELECT 1` 成功才返回 ready |
| 计算队列 | 管理员 `GET /api/v1/runtime/summary` | 观察 `pending` / `waiting` 数量与 `oldest_pending_at` |
| 卡住的执行 | 同上 | 观察 `running` 数量、`running_attempt_count` 与 `oldest_running_at` |
| 失败与规模 | 同上 | 观察 `failed_record_count`、`records_by_status` 和 `total_record_count` |
| 链接规模 | 同上 | `record_link_count`；用于观察跨表依赖规模 |
| 中断恢复 | 管理员 `POST /api/v1/runtime/recover-interrupted` | 只在确认执行器已停止或中断后操作；恢复结果会写入审计 |

`/runtime/summary` 需要 `ADMIN` 令牌。外部监控不得使用成员账号，也不得把 JWT 写入日志。该接口提供当前累计状态快照，不是 Prometheus 格式的时序指标；监控平台应负责定期采样并保存历史。

先以观察模式收集至少一个完整业务周期的基线，再共同确定阈值。建议至少覆盖：健康检查连续失败、最早待处理时间超过业务 SLA、运行记录持续时间异常、失败率相对基线突增、数据库连接/磁盘/慢查询异常、最近备份缺失或校验失败。阈值必须配置在监控平台，不要硬编码成业务规则。

## 4. 备份与隔离恢复演练

以下命令是运维操作模板，不在开发任务中执行。通过 `mysql_config_editor` 配置受限的 `numcounts-ops` 和 `numcounts-restore` 登录路径，避免把密码写入命令行、脚本或 shell 历史。备份目录应位于加密、受访问控制的独立存储中。

```bash
BACKUP_FILE="<受保护备份目录>/numcounts-$(date +%F-%H%M%S).sql"
mysqldump --login-path=numcounts-ops --single-transaction \
  --routines --triggers --events --hex-blob numcounts > "$BACKUP_FILE"
sha256sum "$BACKUP_FILE" > "$BACKUP_FILE.sha256"
```

恢复演练只能使用隔离的临时 MySQL 实例和空的同名数据库，禁止把演练导入生产或仍承载业务的数据库。执行前由第二人核对连接目标和备份校验值：

```bash
sha256sum --check "$BACKUP_FILE.sha256"
mysql --login-path=numcounts-restore --database=numcounts < "$BACKUP_FILE"
```

恢复后至少核验：

1. 表和 Alembic 版本与备份时记录一致；若备份版本为 `20261020_0010`，应确认该版本尚不含 M7 特殊绩效表。
2. `users`、计算记录、执行尝试、成果、正式批次/结果及审计记录数量与备份前记录的核对值一致。
3. API `/health/ready` 正常；管理员能查询运行摘要和已知验收记录；成员只能查询本人正式结果。
4. 记录恢复耗时、数据时间点、缺失项、修复动作和责任人。演练通过后销毁隔离实例及其临时副本，并确认备份保留策略。

生产恢复必须另行走事故审批与变更流程；本手册的演练步骤不授权生产写入、删除或回滚。

## 5. 容量基线与发布检查

先在与预期部署拓扑接近的隔离环境中使用合成数据测试，不把性能测试直接打到生产。每轮记录：记录数/成果数/正式结果数、并发请求数、批次范围、API p50/p95、单条及批次计算耗时、worker 处理速率、MySQL CPU/内存/连接/磁盘/慢查询，以及错误率。

至少覆盖空队列、正常高峰、较大批次、外部执行器超时和 worker 重启恢复。确认业务专家给出周期内用户数、成果量和可接受完成时限后，才能据此制定容量目标。当前为单线程 worker；未完成并发安全和容量验证前不增加 worker 副本。

发布前检查：

- 备份成功且最近一次隔离恢复演练有记录；
- 目标版本、迁移脚本和回滚方案经负责人审阅；迁移仅在单独授权后执行；
- `/health/ready`、管理员运行摘要和成员个人结果冒烟检查通过；
- 告警接收人、值班处置人、观察窗口和回滚决策人明确；
- 前后端版本、变更摘要、测试结果和未完成项已归档。
